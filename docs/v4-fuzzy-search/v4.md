# V4 — Fuzzy Search Fallback with `pg_trgm`

## FTS + GIN + Trigram Similarity

V4 extends the indexed full-text search system from V3 with **typo tolerance**.

V3 already provides:

```text
linguistic query parsing
tokenization
stemming
weighted tsvector
persisted search_vector
GIN indexing
ts_rank_cd()
ts_headline()
```

However, full-text search is not designed primarily to correct spelling mistakes.

For example:

```text
Stored value:
Logitech Keyboard

User query:
logtech keybord
```

The user clearly intends to search for:

```text
logitech keyboard
```

but the words:

```text
logtech
keybord
```

are not necessarily linguistic variants that PostgreSQL full-text search can normalize into the correct lexemes.

V4 introduces PostgreSQL's:

```text
pg_trgm
```

extension as a **fuzzy fallback retrieval strategy**.

The architecture becomes:

```text
User query
    ↓
V3 Full-Text Search
    ↓
Results found?
    │
    ├── YES
    │     ↓
    │   return FTS results
    │
    └── NO
          ↓
       pg_trgm
          ↓
    trigram similarity
          ↓
     fuzzy candidates
          ↓
    similarity ranking
          ↓
        results
```

The important design decision is:

> Fuzzy search does not replace full-text search.

It handles a different problem.

---

# 1. What Problem Does V4 Solve?

V3 can understand linguistic relationships.

For example:

```text
running
runs
run
```

may normalize toward related lexemes.

But:

```text
keybord
```

is not a grammatical form of:

```text
keyboard
```

It is simply misspelled.

Likewise:

```text
logtech
```

is not a linguistic variant of:

```text
logitech
```

The problem has changed from:

```text
language normalization
```

to:

```text
string similarity
```

V4 therefore introduces a second retrieval technique.

---

# 2. Full-Text Search vs Fuzzy Search

These systems solve different problems.

## Full-Text Search

FTS works with linguistic representations.

```text
raw text
   ↓
tokens
   ↓
lexemes
   ↓
stemming
   ↓
tsvector
```

It is useful for:

```text
word normalization
Boolean queries
phrases
stop words
field weighting
relevance ranking
```

Example:

```text
gaming keyboards
```

can match documents containing linguistically related terms.

---

## Trigram Similarity

`pg_trgm` works primarily with **character sequences**.

It helps answer:

```text
How similar are these two strings?
```

Example:

```text
keyboard
```

and:

```text
keybord
```

share many character sequences even though one is misspelled.

That makes trigram similarity useful for:

```text
typos
misspellings
slightly malformed names
brand-name mistakes
similar strings
```


```text

%
<-> 
```

```text
similarity()
%
```

# 4. What Is a Trigram?

A trigram is a sequence of approximately three characters.

Consider:

```text
keyboard
```

A simplified mental model is:

```text
key
eyb
ybo
boa
oar
ard
```

Now consider the misspelling:

```text
keybord
```

Simplified trigrams:

```text
key
eyb
ybo
bor
ord
```

Several pieces overlap:

```text
key
eyb
ybo
```

Therefore the strings have measurable similarity.

Conceptually:

```text
keyboard
     ≈
keybord
```

The strings are not equal.

They are not linguistically equivalent.

But they share enough character structure to be considered similar.

---

# 5. `similarity()`

PostgreSQL provides:

```sql
similarity(text, text)
```

Example:

```sql
SELECT similarity(
    'keyboard',
    'keybord'
);
```

The function returns a score between approximately:

```text
0
```

and:

```text
1
```

Conceptually:

```text
0.0
→ almost no similarity

1.0
→ identical strings
```

For example:

```sql
SELECT similarity(
    'logitech',
    'logtech'
);
```

should produce a relatively meaningful similarity score.

While:

```sql
SELECT similarity(
    'keyboard',
    'banana'
);
```

should produce a much weaker score.

---

# 6. Similarity Scores Are Not Percentages

A value such as:

```text
0.62
```

should not automatically be displayed as:

```text
62% correct
```

The value represents trigram similarity according to PostgreSQL's algorithm.

It is useful primarily for:

```text
comparison
ranking
thresholding
```

For example:

```text
Product A → 0.71
Product B → 0.54
Product C → 0.32
```

Product A is the strongest fuzzy candidate among those products.

---

# 7. The `%` Operator

`pg_trgm` also provides:

```sql
text % text
```

The operator answers approximately:

```text
Are these strings similar enough
to satisfy the configured similarity threshold?
```

Example SQL:

```sql
SELECT
    'keyboard' % 'keybord';
```

The result is Boolean:

```text
true
```

or:

```text
false
```

Therefore there are two separate concepts:

```text
%
```

for filtering candidates,

and:

```text
similarity()
```

for calculating their scores.

---

# 8. Similarity Threshold

The `%` operator uses PostgreSQL's configured trigram similarity threshold.

Inspect it with:

```sql
SHOW pg_trgm.similarity_threshold;
```

A typical value is:

```text
0.3
```

Conceptually:

```text
similarity >= threshold
        ↓
candidate may satisfy %
```

The exact threshold affects search behavior dramatically.

A high threshold can produce:

```text
fewer
more precise
fuzzy candidates
```

A lower threshold can produce:

```text
more
but potentially noisier
results
```

Threshold tuning therefore becomes part of fuzzy-search relevance engineering.

---

# 9. V4 Searchable Fuzzy Fields

The first V4 implementation applies trigram similarity to:

```text
name
brand
category
```

It intentionally does not start by fuzzy-searching the entire description.

Why?

Descriptions can contain large amounts of unrelated text.

For a query:

```text
logtech keyboard
```

a long description may contain many character sequences that create noisy similarity signals.

Fields such as:

```text
name
brand
category
```

are shorter and generally more useful for typo recovery.

---

# 10. Fuzzy Search Query

The fuzzy retrieval query is:

```sql
WITH search_input AS (
    SELECT %s::text AS query
)

SELECT
    p.id,
    p.name,
    p.description,
    p.brand,
    p.category,
    p.tags,
    p.price,
    p.rating,
    p.stock,
    p.created_at,

    GREATEST(
        similarity(
            p.name,
            q.query
        ),

        similarity(
            COALESCE(p.brand, ''),
            q.query
        ),

        similarity(
            COALESCE(p.category, ''),
            q.query
        )
    ) AS fuzzy_score

FROM products AS p

CROSS JOIN search_input AS q

WHERE
       p.name % q.query
    OR COALESCE(p.brand, '') % q.query
    OR COALESCE(p.category, '') % q.query

ORDER BY
    fuzzy_score DESC,
    p.id ASC;
```

When used through Psycopg's `%s` parameter style, the literal PostgreSQL `%` operator may appear in the Python SQL string as:

```sql
%%
```

For example:

```python
WHERE p.name %% q.query
```

while PostgreSQL itself receives the trigram:

```sql
%
```

operator.

---

# 11. `search_input`

V4 uses:

```sql
WITH search_input AS (
    SELECT %s::text AS query
)
```

instead of repeating the Python parameter many times.

Without it, the query might need:

```text
query
query
query
query
query
query
```

as separate parameters.

Instead:

```python
params = (query,)
```

is enough.

The search query becomes available as:

```sql
q.query
```

throughout the SQL statement.

---

# 12. Why `CROSS JOIN` Is Used

The CTE:

```sql
search_input
```

produces exactly one row.

Therefore:

```sql
CROSS JOIN search_input AS q
```

conceptually attaches the same query value to every candidate product.

It does not create a large Cartesian explosion because:

```text
search_input rows = 1
```

Conceptually:

```text
Product 1 + query
Product 2 + query
Product 3 + query
...
```

This allows expressions such as:

```sql
similarity(
    p.name,
    q.query
)
```

without repeating the parameter placeholder.

---

# 13. `COALESCE()`

Fields such as:

```text
brand
category
```

can potentially contain:

```text
NULL
```

Similarity functions require useful text inputs.

Therefore:

```sql
COALESCE(
    p.brand,
    ''
)
```

turns:

```text
NULL
```

into:

```text
''
```

The same technique is used for:

```sql
COALESCE(
    p.category,
    ''
)
```

This prevents missing values from interfering with similarity calculations.

---

# 14. Multi-Field Similarity

V4 evaluates:

```text
name similarity
brand similarity
category similarity
```

independently.

For example:

```text
Query:
logtech
```

Product:

```text
name:
Logitech Wireless Keyboard

brand:
Logitech

category:
Keyboards
```

The scores might conceptually resemble:

```text
name       → 0.38
brand      → 0.72
category   → 0.05
```

V4 then uses:

```sql
GREATEST(...)
```

to select:

```text
0.72
```

as the product's:

```text
fuzzy_score
```

---

# 15. Why `GREATEST()`?

The goal is to allow a strong signal from any important field.

Suppose the user searches:

```text
logtech
```

The product name may be long:

```text
Logitech MX Mechanical Wireless Keyboard
```

which can dilute whole-string similarity.

But the brand field:

```text
Logitech
```

is extremely close to:

```text
logtech
```

Therefore:

```sql
GREATEST(
    name_similarity,
    brand_similarity,
    category_similarity
)
```

allows the strongest field to represent the product.

---

# 16. Fuzzy Candidate Filtering

The query uses:

```sql
WHERE
       p.name % q.query
    OR COALESCE(p.brand, '') % q.query
    OR COALESCE(p.category, '') % q.query
```

This means a product becomes a candidate when at least one field is sufficiently similar.

Conceptually:

```text
name matches threshold?
    OR
brand matches threshold?
    OR
category matches threshold?
```

If any condition succeeds:

```text
product becomes a fuzzy candidate
```

---

# 17. Fuzzy Ranking

Candidates are sorted using:

```sql
ORDER BY
    fuzzy_score DESC,
    p.id ASC;
```

The highest similarity score appears first.

Example:

```text
Product A → 0.74
Product B → 0.61
Product C → 0.43
```

Result order:

```text
A
B
C
```

The secondary:

```sql
p.id ASC
```

provides deterministic ordering when two products receive the same fuzzy score.

This is especially useful once pagination is introduced.

---

# 18. Multi-Word Query Limitation

There is an important limitation in the current algorithm.

Consider:

```text
logtech keyboard
```

The fuzzy query compares the complete string against each individual field.

For example:

```sql
similarity(
    brand,
    'logtech keyboard'
)
```

may effectively compare:

```text
Logitech
```

with:

```text
logtech keyboard
```

The additional:

```text
keyboard
```

reduces whole-field similarity.

Likewise:

```sql
similarity(
    category,
    'logtech keyboard'
)
```

may compare:

```text
Keyboards
```

against the entire query.

Therefore the current V4 implementation is intentionally a **baseline fuzzy algorithm**, not a final production-grade spell-correction system.

---

# 19. Why This Limitation Matters

Single-term typo:

```text
logtech
```

may work very well.

Single-term typo:

```text
keybord
```

may also work well.

But:

```text
logtech keybord
```

introduces multiple misspelled tokens.

A more sophisticated system might later:

```text
split the query into terms
score individual terms
generate query corrections
use word_similarity()
use strict_word_similarity()
use dictionaries
use historical query data
use embeddings
use machine-learned query rewriting
```

V4 intentionally stays focused on the fundamental PostgreSQL fuzzy-search mechanism.

---

# 20. Fuzzy Search Is a Fallback

The important V4 architecture is not:

```text
all searches
    ↓
pg_trgm
```

Instead:

```text
all searches
    ↓
V3 FTS
```

If FTS works:

```text
return FTS results
```

Only if FTS fails:

```text
activate fuzzy retrieval
```

Conceptually:

```text
query
  ↓
FTS
  ↓
count > 0?
  │
  ├── yes
  │    ↓
  │  return
  │
  └── no
       ↓
    pg_trgm
       ↓
    return fuzzy
```

---

# 21. Why FTS Should Remain Primary

FTS already understands:

```text
lexemes
stemming
Boolean search
phrases
field weights
search relevance
```

Trigram similarity does not replace those capabilities.

A correctly typed query such as:

```text
gaming mechanical keyboard
```

should normally use:

```text
FTS + GIN
```

rather than treating the entire query as a fuzzy character-comparison problem.

Therefore the algorithms are complementary:

```text
FTS
→ semantic / linguistic retrieval

pg_trgm
→ character-similarity recovery
```

```text
products
```

to evaluate:

```text
name % query

```

The execution plan may therefore include:

```text
Sequential Scan
```

Conceptually:

```text

    ↓
calculate trigram conditions
    ↓
reject non-similar rows
    ↓
calculate fuzzy_score
    ↓

```

# 30. `Rows Removed by Filter`

A fuzzy sequential scan may show:

```text
Rows Removed by Filter
```

For example:

```text

      ↓
99,940 rejected
      ↓
60 fuzzy candidates
```

This reveals the amount of work performed before PostgreSQL found the relevant candidates.

It is similar to the performance problem observed earlier before indexing FTS.

# 31. Trigram Indexes

`pg_trgm` supports specialized indexes.

A trigram GIN index can conceptually be created for a field such as:

```sql
CREATE INDEX idx_products_name_trgm
ON products
USING GIN (
    name gin_trgm_ops
);
```

Additional indexes could potentially be created for:

```text
brand
category
```

However, indexing every fuzzy field introduces:

```text
storage cost
write overhead
index maintenance
additional architecture complexity
```

Therefore V4 should first establish correct fuzzy behavior before blindly indexing every text field.

---

# 32. Why Not Reuse the FTS GIN Index?

V3 already has:

```text
idx_products_search_vector
```

but that index belongs to:

```text
tsvector
```

and FTS operators such as:

```text
@@
```

The trigram query operates on:

```text
name
brand
category
```

using trigram operators such as:

```text
%
```

These are different operator families and different retrieval representations.

Therefore:

```text
FTS GIN index
```

does not automatically optimize:

```text
pg_trgm similarity
```

A trigram index needs the appropriate operator class such as:

```text
gin_trgm_ops
```

---

# 33. FTS GIN vs Trigram GIN

They may both use the word:

```text
GIN
```

but they index different representations.

## FTS GIN

Indexes:

```text
tsvector lexemes
```

Used for:

```sql
search_vector @@ tsquery
```

---

## Trigram GIN

Indexes:

```text
character trigrams
```

Used for trigram-supported operations such as:

```sql
name % query
```

The index mechanism is related.

The indexed data and operator classes are different.

---

# 34. Why Not Fuzzy Search Descriptions?

Consider:

```text
query:
logtech
```

and a description containing hundreds of characters.

Whole-description trigram similarity can be significantly diluted because the strings differ greatly in length and content.

A short brand field:

```text
Logitech
```

provides a much cleaner comparison.

Therefore the current V4 fuzzy fields focus on:

```text
name
brand
category
```

rather than:

```text
description
```

This is a deliberate relevance choice.

---

# 35. Tags Are Not Yet Included

The existing product schema contains:

```sql
tags TEXT[]
```

V4 does not initially include tags in the trigram query.

They could later be converted:

```sql
array_to_string(
    tags,
    ' '
)
```

and compared.

However, that would introduce another fuzzy signal and additional performance considerations.

V4 intentionally begins with the clearest textual fields.

---

# 36. FTS Ranking vs Fuzzy Ranking

V3 uses:

```sql
ts_rank_cd()
```

while fuzzy fallback uses:

```sql
similarity()
```

These scores represent different concepts.

Therefore:

```text
FTS rank
```

and:

```text
fuzzy_score
```

should not be directly compared as though they were the same scale.

For example:

```text
FTS rank = 0.31

fuzzy_score = 0.61
```

does not mean fuzzy search is:

```text
twice as relevant
```

They are generated by different algorithms.

The frontend should label them separately.

---

# 37. Deterministic Ordering

V4 uses:

```sql
ORDER BY
    fuzzy_score DESC,
    p.id ASC;
```

The second key:

```text
id ASC
```

ensures stable ordering when two products have identical fuzzy scores.

Without a deterministic tie-breaker:

```text
Product A → 0.52
Product B → 0.52
```

could appear in an unstable order between executions.

Stable ordering becomes particularly important for pagination.

# 42. Why Fallback Architecture Matters

Suppose fuzzy search were used for every query.

Then a perfectly valid query:

```text
gaming mechanical keyboard
```

would skip the richer linguistic machinery provided by:

```text
tsquery
weighted tsvector
GIN FTS
ts_rank_cd()
```

That would throw away useful search behavior.

Instead:

```text
FTS handles valid linguistic queries.
```

and:

```text
pg_trgm handles character-level recovery.
```

This separation makes the system easier to:

```text
reason about
benchmark
debug
tune
extend
```

---

# 43. False Positives

Fuzzy search introduces a new tradeoff.

Lowering the similarity threshold can recover more typos, but may also produce unrelated candidates.

For example:

```text
query:
mouse
```

could potentially share character patterns with strings that are not truly relevant.

Therefore fuzzy search involves balancing:

```text
recall
```

against:

```text
precision
```

A system with high recall retrieves more possibilities.

A system with high precision returns fewer but more accurate possibilities.

---

# 44. Fuzzy Search Is Not Spell Checking

`pg_trgm` does not necessarily know:

```text
keybord
```

should be corrected specifically to:

```text
keyboard
```

It primarily knows that:

```text
keybord
```

and:

```text
keyboard
```

have strong string similarity.

That is an important distinction.

V4 performs:

```text
fuzzy retrieval
```

rather than implementing a complete language-aware spell-checking system.

---

# 45. Search vs Query Correction

There are two possible architectures.

## Fuzzy Retrieval

```text
keybord
   ↓
search products directly
   ↓
products containing similar text
```

This is what V4 demonstrates.

---

## Query Correction

Another system could first generate:

```text
Did you mean:
keyboard?
```

then run:

```text
keyboard
```

through normal FTS.

That would be a separate query-understanding layer.

V4 does not require such a correction stage.

---

# 46. Why V4 Is Important

A technically correct search engine can still feel broken to users if small typing mistakes produce:

```text
0 results
```

Real user input is messy.

Users type:

```text
brand names incorrectly
missing characters
extra characters
transposed letters
partial product names
```

V4 introduces tolerance for that imperfect input.

This shifts the system from:

```text
The query must fit the search engine
```

toward:

```text
The search engine attempts to recover
the user's intent.
```

# 47. Current Limitations

V4 still has several limitations.

```text
whole-query similarity can be weak for multi-word searches
similarity threshold may require tuning
fuzzy ranking is relatively simple
large fuzzy scans may be expensive
no historical query behavior is used
no personalized ranking exists
no machine learning is involved
no semantic embeddings are used
```

These are intentional.

The purpose of V4 is to understand and implement the fundamental fuzzy-retrieval layer before introducing more advanced ranking systems.

# 49. Final Mental Model

V3 asks:

```text
Can PostgreSQL efficiently retrieve products
that linguistically satisfy this query?
```

V4 adds:

```text
What if the query itself is slightly wrong?
```

The solution is:

```text
FTS first
    ↓
if necessary
    ↓
character-similarity recovery
```

# 50. V4 Summary

V4 introduces:

```text
PostgreSQL pg_trgm
```

and:

```text
trigram similarity
```

without discarding the search architecture built in V3.

The final behavior is:

```text
Correct query
    ↓
FTS + GIN
    ↓
ranked linguistic results


Misspelled query
    ↓
FTS fails
    ↓
pg_trgm fallback
    ↓
similarity candidates
    ↓
fuzzy_score
    ↓
ranked fuzzy results
```

In one sentence:

> **V3 makes correct searches efficient; V4 helps the system recover when the user's query is imperfect.**
