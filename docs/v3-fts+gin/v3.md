## V3 — Indexed Full-Text Search with GIN

### FTS + GIN

V3 keeps the full-text search behavior introduced in V2, but changes how PostgreSQL retrieves matching products.

V2 already understands language through:

```text
tokens
lexemes
stemming
stop words
tsvector
tsquery
@@
ts_rank_cd()
ts_headline()
```

The problem is performance.

In V2, PostgreSQL constructs the searchable `tsvector` during query execution and may scan the product table row by row.

V3 introduces two changes:

```text
1. Persist the search_vector on the products table
2. Create a GIN index over that vector
```

The search semantics remain the same.

The retrieval strategy changes.

---

# 1. V2 Recap

V2 builds the search vector inside the query.

Conceptually:

```text
products
    ↓
read product
    ↓
to_tsvector(name)
to_tsvector(brand)
to_tsvector(category)
to_tsvector(tags)
to_tsvector(description)
    ↓
set weights
    ↓
combine vectors
    ↓
@@ tsquery
    ↓
keep matching row
```

For a table containing approximately:

```text
100,000 products
```

PostgreSQL may need to perform this work across a large portion of the table.

This gives us good linguistic search, but not efficient retrieval.

---

# 2. The V3 Goal

V3 answers:

```text
How can PostgreSQL find matching lexemes without scanning and rebuilding search vectors across the entire dataset?
```

The solution is an **inverted index**.

PostgreSQL provides this through:

```sql
GIN
```

which stands for:

```text
Generalized Inverted Index
```

---

# 3. Persisting `search_vector`

Instead of calculating:

```sql
to_tsvector(...)
```

inside every search query, V3 stores the resulting vector as part of each product row.

The new column is:

```sql
search_vector tsvector
```

The table conceptually becomes:

```text
products
├── id
├── name
├── description
├── brand
├── category
├── tags
├── price
├── rating
├── stock
├── created_at
└── search_vector
```

The important difference is:

```text
V2:
search_vector exists only while the query is running

V3:
search_vector is persisted with the product
```

---

# 4. Generated Search Vector

The vector should use the exact same field weights as V2.

```text
A → name
B → brand
B → category
C → tags
D → description
```

The generated column can be created as:

```sql
ALTER TABLE products

ADD COLUMN search_vector tsvector

GENERATED ALWAYS AS (

    setweight(
        to_tsvector(
            'english',
            COALESCE(name, '')
        ),
        'A'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(brand, '')
        ),
        'B'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(category, '')
        ),
        'B'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(
                array_to_string(tags, ' '),
                ''
            )
        ),
        'C'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(description, '')
        ),
        'D'
    )

) STORED;
```

This preserves the same ranking strategy used by V2.

---

# 5. Why `GENERATED ALWAYS`

The search vector depends entirely on other product fields.

For example:

```text
name
brand
category
tags
description
```

If any of these values change, the search representation must also change.

Without automatic generation, application code would need to remember to update:

```text
product data
+
search_vector
```

every time a product changes.

That creates a synchronization problem.

Using:

```sql
GENERATED ALWAYS AS (...) STORED
```

delegates this responsibility to PostgreSQL.

For example:

```sql
UPDATE products
SET name = 'Mechanical Gaming Keyboard'
WHERE id = 42;
```

PostgreSQL automatically recalculates the corresponding:

```text
search_vector
```

No additional application update is required.

---

# 6. Why `STORED`

The generated vector is physically stored rather than recalculated every time it is referenced.

Conceptually:

```text
INSERT / UPDATE
        ↓
calculate tsvector once
        ↓
store it with the row
```

instead of:

```text
every SELECT
    ↓
recalculate tsvector
```

This moves work away from read-time search queries.

That is especially useful for search-heavy systems where products are queried much more often than they are modified.

---

# 7. Creating the GIN Index

Once `search_vector` exists, V3 adds:

```sql
CREATE INDEX idx_products_search_vector

ON products

USING GIN (search_vector);
```

This is the defining optimization in V3.

The index is built over the normalized lexemes contained in the vector.

---

# 8. What an Inverted Index Means

A normal table is organized conceptually around rows:

```text
Product 1 → words
Product 2 → words
Product 3 → words
```

An inverted index reverses that relationship.

Conceptually:

```text
lexeme → matching products
```

For example:

```text
'keyboard'
    → 12
    → 45
    → 91
    → 1042

'game'
    → 12
    → 78
    → 91
    → 882

'mechan'
    → 12
    → 91
    → 301
```

Now consider the query:

```text
gaming mechanical keyboard
```

PostgreSQL does not necessarily need to inspect every product first.

It can identify candidate rows through the index entries associated with the normalized search terms.

---

# 9. GIN

GIN stands for:

```text
Generalized Inverted Index
```

It is well suited for values containing multiple searchable elements.

Examples include:

```text
tsvector
arrays
JSONB
```

For full-text search, one product vector contains many lexemes.

GIN maintains index entries that allow PostgreSQL to efficiently answer questions such as:

```text
Which rows contain this lexeme?
```

or:

```text
Which rows satisfy this tsquery?
```

---

# 10. V3 Search Query

Because the search vector already exists, the V3 SQL becomes simpler.

The V2 CTE:

```sql
WITH searchable_products AS (...)
```

is no longer necessary.

V3 can use:

```sql
WITH search_input AS (

    SELECT websearch_to_tsquery(
        'english',
        %s
    ) AS query

)

SELECT
    p.id,
    p.name,
    p.description,
    p.brand,
    p.category,
    p.tags,
    p.price,
    p.rating,
    p.stock,
    p.created_at,

    ts_rank_cd(
        p.search_vector,
        q.query
    ) AS rank,

    ts_headline(
        'english',
        COALESCE(p.description, ''),
        q.query,
        'StartSel=<mark>, StopSel=</mark>, MaxWords=30, MinWords=10'
    ) AS headline

FROM products AS p

CROSS JOIN search_input AS q

WHERE p.search_vector @@ q.query

ORDER BY
    rank DESC,
    p.id ASC;
```

The search logic remains familiar.

The major difference is:

```sql
p.search_vector
```

is now an existing stored column.

---

# 11. What Remains Identical to V2

For a fair benchmark, V3 intentionally keeps the following unchanged:

```text
English text-search configuration
field selection
field weights
websearch_to_tsquery()
@@
ts_rank_cd()
ts_headline()
result ordering
```

Therefore the experimental change is primarily:

```text
V2:
runtime vector construction + no FTS index

V3:
stored vector + GIN index
```

This allows performance differences to be attributed to retrieval architecture rather than changed search semantics.

---

# 12. V2 vs V3

| Feature                        | V2                 | V3                   |
| ------------------------------ | ------------------ | -------------------- |
| Search model                   | Full-text search   | Full-text search     |
| `tsvector`                     | Built during query | Stored column        |
| Field weights                  | A/B/C/D            | Same A/B/C/D         |
| `tsquery`                      | Yes                | Yes                  |
| `@@` matching                  | Yes                | Yes                  |
| Ranking                        | `ts_rank_cd()`     | Same                 |
| Headlines                      | `ts_headline()`    | Same                 |
| Specialized FTS index          | No                 | **GIN**              |
| Likely candidate retrieval     | Table scan         | Index-assisted       |
| Vector recalculated per search | Yes                | No                   |
| Main goal                      | semantics          | retrieval efficiency |

The critical distinction is:

```text
V2 improves search quality.

V3 improves how efficiently PostgreSQL finds the same matches.
```

---

# 13. Expected Execution Plan Change

In V2, PostgreSQL may produce a plan resembling:

```text
Sequential Scan
    ↓
Filter using @@
    ↓
Rank
    ↓
Sort
```

After adding the GIN index, V3 may produce something closer to:

```text
Bitmap Index Scan
    ↓
Bitmap Heap Scan
    ↓
Rank
    ↓
Sort
```

This is one of the most important execution-plan changes in the project.

---

# 14. Bitmap Index Scan

A plan may contain:

```text
Bitmap Index Scan
```

This means PostgreSQL is using an index to identify candidate row locations.

For V3, the index may be:

```text
idx_products_search_vector
```

Conceptually:

```text
tsquery
   ↓
GIN index
   ↓
matching row locations
```

The index does not necessarily return the complete product row.

It primarily helps identify where candidate rows are located.

---

# 15. Bitmap Heap Scan

After obtaining candidate locations, PostgreSQL may perform:

```text
Bitmap Heap Scan
```

The heap is the actual table storage.

Conceptually:

```text
GIN index
    ↓
candidate row locations
    ↓
Bitmap Heap Scan
    ↓
retrieve actual products
```

This is why execution plans often contain both:

```text
Bitmap Index Scan
```

and:

```text
Bitmap Heap Scan
```

They perform different jobs.

---

# 16. Why Not Always an `Index Scan`?

GIN indexes are commonly used through bitmap execution strategies.

So a successful V3 plan does not need to literally say:

```text
Index Scan
```

A plan such as:

```text
Bitmap Heap Scan
    ↓
Bitmap Index Scan
```

is still evidence that the GIN index is being used.

The UI should therefore avoid simplifying:

```text
Index Scan = indexed
Sequential Scan = unindexed
```

into an overly rigid rule.

Instead, it should recognize multiple index-assisted plan nodes.

---

# 17. PostgreSQL May Still Choose a Sequential Scan

Creating an index does not force PostgreSQL to use it.

The query planner chooses the execution strategy it estimates will cost the least.

Suppose a search query matches:

```text
90,000 out of 100,000 products
```

Using the index may require:

```text
index lookup
+
large bitmap
+
many heap fetches
```

At that point, reading the table sequentially may genuinely be cheaper.

Therefore PostgreSQL may still choose:

```text
Seq Scan
```

even though the GIN index exists.

This is not automatically a failure.

---

# 18. Selectivity

The usefulness of an index depends heavily on **selectivity**.

A selective query matches a relatively small portion of the table.

For example:

```text
"mechanical ergonomic keyboard"
```

might match:

```text
120 products out of 100,000
```

This is highly selective.

The GIN index can be very useful.

A broad query such as:

```text
wireless
```

might match:

```text
40,000 products
```

The benefit may be smaller.

An extremely common term may cause PostgreSQL to prefer a sequential scan.

Therefore benchmark queries should include:

```text
high-selectivity queries
medium-selectivity queries
broad queries
```

rather than testing only one term.

---

# 19. GIN Does Not Automatically Sort by Relevance

This is a crucial distinction.

The GIN index helps find products that satisfy:

```sql
p.search_vector @@ q.query
```

It does not normally return those rows already sorted by:

```sql
ts_rank_cd(...)
```

Therefore the execution flow can still be:

```text
GIN index
    ↓
find matching candidates
    ↓
retrieve products
    ↓
calculate ts_rank_cd()
    ↓
sort by rank
```

So V3 may still contain:

```text
Sort
```

in the execution plan.

That does not mean the GIN index failed.

The index optimized **candidate retrieval**, not relevance ordering.

---

# 20. Matching vs Ranking

V3 reinforces the distinction between two separate search-system problems.

### Matching

```sql
p.search_vector @@ q.query
```

answers:

```text
Does this product satisfy the search query?
```

GIN primarily helps this stage.

### Ranking

```sql
ts_rank_cd(
    p.search_vector,
    q.query
)
```

answers:

```text
Among the matching products, which products should appear first?
```

GIN does not eliminate this calculation.

---

# 21. Write Cost vs Read Benefit

Indexes are not free.

V3 improves reads, but introduces additional work during writes.

When a product is inserted:

```text
INSERT
    ↓
generate search_vector
    ↓
store row
    ↓
update GIN index
```

When a searchable field changes:

```text
UPDATE
    ↓
recalculate search_vector
    ↓
update row
    ↓
update GIN index
```

Therefore:

```text
faster search
```

comes with:

```text
more storage
+
more insert/update work
```

This is a fundamental database tradeoff.

---

# 22. Storage Cost

V3 stores additional information in two places.

First:

```text
products.search_vector
```

stores the normalized vector.

Second:

```text
idx_products_search_vector
```

stores the GIN index structure.

Therefore V3 consumes more database storage than V2.

That is expected.

The question is not:

```text
Does indexing cost storage?
```

It does.

The useful question is:

```text
Is the additional storage and write cost worth the reduction in search work?
```

The benchmark helps answer that.

---

# 23. Insert and Update Behavior

Consider:

```sql
INSERT INTO products (
    name,
    description,
    brand,
    category,
    tags,
    price,
    rating,
    stock
)
VALUES (...);
```

The application does not explicitly supply:

```text
search_vector
```

because PostgreSQL generates it.

Likewise:

```sql
UPDATE products
SET description = 'Updated mechanical keyboard description'
WHERE id = 42;
```

causes the generated vector to be recalculated automatically.

This keeps search data consistent with product data.

---

# 24. Why Not Build the Vector in Python?

The application could theoretically construct search representations itself.

That would introduce several problems:

```text
duplicated linguistic logic
application/database synchronization
more application complexity
risk of stale vectors
difficulty guaranteeing identical PostgreSQL parsing
```

Keeping vector construction inside PostgreSQL ensures that the same database text-search configuration controls both:

```text
document normalization
and
query normalization
```

---

# 25. V3 Execution Pipeline

A selective query can now conceptually follow:

```text
User query
    ↓
websearch_to_tsquery()
    ↓
tsquery
    ↓
GIN index lookup
    ↓
candidate row locations
    ↓
Bitmap Heap Scan
    ↓
matching products
    ↓
ts_rank_cd()
    ↓
Sort
    ↓
Results
```

Compare this with V2:

```text
User query
    ↓
tsquery
    ↓
scan products
    ↓
construct vectors
    ↓
test @@
    ↓
rank matches
    ↓
sort
```

That architectural difference is the purpose of V3.

When PostgreSQL uses the GIN index, the raw plan may include:

```text

```

The UI should expose this clearly.

For example:

```text

```

---

# 28. Shared Buffer Behavior

V3 continues collecting:

```text
BUFFERS
```

because execution time alone is not enough.

A plan may report:

```text
Shared Hit Blocks
Shared Read Blocks
```

A shared hit means PostgreSQL found a required page in its shared buffer cache.

A shared read means PostgreSQL had to read a page into that cache.

This matters when comparing repeated benchmark runs.

A query run for the first time may behave differently from the same query executed immediately afterward.

---

# 29. Warm Cache vs Cold Cache

Benchmark results can vary depending on cache state.

For example:

```text
First execution
    ↓
more pages may need to be read

Second execution
    ↓
many pages may already be cached
```

Therefore a single timing result should not be treated as universally representative.

For a stronger benchmark, record multiple runs and distinguish:

```text
cold-ish execution
warm execution
median execution
```

when possible.

---

# 30. Application Time Still Matters

The backend continues measuring:

```text
application_time_ms
```

using Python's:

```python
perf_counter()
```

This includes work observed from the application side.

Conceptually:

```text
Python
    ↓
Psycopg
    ↓
PostgreSQL
    ↓
result transfer
    ↓
Python rows
```

GIN primarily improves PostgreSQL retrieval behavior, but the effect can also reduce application-observed latency.

---

# 31. PostgreSQL Execution Time

The execution plan separately reports:

```text
Execution Time
```

This represents PostgreSQL's server-side execution measurement.

Therefore the benchmark continues to distinguish:

```text
Application Time
```

from:

```text
PostgreSQL Execution Time
```

These values should not be treated as interchangeable.

---

# 32. Memory Measurement

The Python backend continues measuring:

```text
current traced memory
peak traced memory
```

using:

```python
tracemalloc
```

This remains application-side memory instrumentation.

GIN memory usage inside PostgreSQL is not measured by `tracemalloc`.

So:

```text
Python peak memory
≠
PostgreSQL memory consumption
```

The UI should continue making that distinction explicit.

# 33. Benchmark Fairness

V3 should be compared against V2 using the same queries.

For example:

```text
gaming mechanical keyboard
wireless mouse
apple OR samsung
"noise cancelling headphones"
gaming -wireless
```

The following should remain identical:

```text
dataset
query
returned columns
ranking function
headline generation
text-search configuration
field weights
```

The architecture changes.

The search semantics do not.

---

# 34. The Independent Variable

For the V2 → V3 experiment, think of the independent variable as:

```text
Persisted tsvector + GIN index
```

Everything else should remain controlled.

That makes the performance comparison meaningful.

If V3 simultaneously changed:

```text
ranking
query parser
weights
result limit
search fields
```

then the benchmark could no longer isolate the effect of indexing.

---

# 35. Expected Performance Outcome

For selective queries, V3 should generally reduce the amount of unnecessary row scanning compared with V2.

However:

```text
GIN does not guarantee every query will be faster.
```

Performance depends on:

```text
query selectivity
number of matches
cache state
table size
index size
ranking cost
headline cost
result count
planner estimates
```

The correct approach is to inspect actual plans and measurements rather than assuming:

```text
index = always fast
```

---

# 36. Why V3 Matters

V2 proved:

```text
PostgreSQL can behave like a linguistic search engine.
```

V3 proves something different:

```text
Search semantics and retrieval architecture are separate concerns.
```

You can have excellent search semantics and still have poor execution behavior.

The GIN index addresses candidate retrieval without changing the linguistic model.

---


The key systems lesson is:

```text

```

# 38. V2 vs V3 Mental Model

### V2

```text
"What does this query mean?"

PostgreSQL:
I understand it.

"Where are the matching products?"

PostgreSQL:
Give me a moment while I inspect the table.
```

### V3

```text
"What does this query mean?"

PostgreSQL:
Same answer as V2.

"Where are the matching products?"

PostgreSQL:
I have an inverted index for that.
```

That is the architectural evolution.

---

# 39. V3 Limitation

V3 solves a major retrieval problem, but it does not complete the search system.

Even with GIN:

```text
ranking can still be expensive
sorting can still be expensive
broad queries can still return many candidates
ts_headline() still consumes work
business relevance may still be weak
typos still may not match
```

For example:

```text
logtech keyboard
```

may fail to match:

```text
Logitech Keyboard
```

because standard FTS is not inherently typo tolerant.

That belongs to a later search stage.

# 40. V3 Summary

V3 introduces:

```text
Stored weighted tsvector
+
GIN inverted index
```

while preserving:

```text
V2 linguistic retrieval
V2 weighting
V2 tsquery parsing
V2 ranking
V2 highlighting
```

The progression is now:

```text
V1
Raw substring search

        ↓

V2
Linguistic full-text search
without specialized indexing

        ↓

V3
The same linguistic search
with persisted vectors
and GIN-assisted retrieval
```

In one sentence:

```text
V2 teaches PostgreSQL what to search.

V3 gives PostgreSQL an efficient structure for finding it.
```
