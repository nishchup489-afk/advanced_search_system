# V3 — Indexed Full-Text Search with GIN

## FTS + Persisted Search Vector + Trigger + GIN

V3 keeps the linguistic search behavior introduced in V2, but changes how PostgreSQL stores and retrieves the searchable representation of each product.

V2 already provides:

```text
tokenization
lexemes
stemming
stop-word handling
weighted fields
tsvector
tsquery
websearch_to_tsquery()
@@
ts_rank_cd()
ts_headline()
```

The problem is that V2 constructs each product's `tsvector` during every search.

V3 moves that work out of the search path.

The new architecture is:

```text
Product INSERT / searchable-field UPDATE
                    ↓
              PostgreSQL trigger
                    ↓
          build weighted tsvector
                    ↓
          store in search_vector
                    ↓
            maintain GIN index
```

Searches can then use the already-persisted vector:

```text
User query
    ↓
websearch_to_tsquery()
    ↓
GIN index
    ↓
candidate products
    ↓
@@ matching
    ↓
ts_rank_cd()
    ↓
sorted results
```

---

# 1. V2 Problem

In V2, every query constructs a vector using:

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(name, '')
    ),
    'A'
)
||
setweight(...)
||
setweight(...)
```

This happens while the search is running.

Conceptually:

```text
100,000 products
        ↓
read product 1
        ↓
construct tsvector
        ↓
test @@

read product 2
        ↓
construct tsvector
        ↓
test @@

...

read product 100,000
        ↓
construct tsvector
        ↓
test @@
```

V2 improves **search semantics**, but it can still perform expensive work over a large portion of the table.

---

# 2. V3 Goal

V3 answers:

```text
Why rebuild the same product search vector
every time someone searches?
```

The product's searchable representation only changes when searchable product data changes.

Therefore V3 calculates the vector during the **write path** instead of the **read/search path**.

The searchable fields remain:

```text
name
brand
category
tags
description
```

The weights remain:

```text
A → name
B → brand
B → category
C → tags
D → description
```

This keeps V2 and V3 search semantics consistent.

---

# 3. Add the Persisted `search_vector` Column

V3 adds a normal PostgreSQL `tsvector` column:

```sql
ALTER TABLE products
ADD COLUMN search_vector tsvector;
```

The table now conceptually becomes:

```text
products
├── id
├── name
├── description
├── brand
├── category
├── tags
├── price
├── rating
├── stock
├── created_at
└── search_vector
```

Unlike V2, the vector now exists persistently as part of each product row.

---

# 4. Why a Normal Column Instead of a Generated Column?

The original design attempted to use:

```sql
GENERATED ALWAYS AS (...) STORED
```

However, PostgreSQL rejected the expression:

```text
ERROR: generation expression is not immutable
```

The searchable expression contains:

```sql
array_to_string(tags, ' ')
```

as part of converting the `TEXT[]` tags array into text.

PostgreSQL generated-column expressions are subject to strict immutability requirements.

Therefore V3 uses a different architecture:

```text
normal tsvector column
+
database trigger
```

The trigger keeps the vector synchronized automatically.

This still achieves the important V3 requirement:

```text
Do not construct the complete document tsvector
during every search query.
```

---

# 5. Trigger-Based Search Vector Maintenance

A PostgreSQL trigger function generates the vector.

```sql
CREATE OR REPLACE FUNCTION update_product_search_vector()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN

    NEW.search_vector :=

        setweight(
            to_tsvector(
                'english',
                COALESCE(NEW.name, '')
            ),
            'A'
        )

        ||

        setweight(
            to_tsvector(
                'english',
                COALESCE(NEW.brand, '')
            ),
            'B'
        )

        ||

        setweight(
            to_tsvector(
                'english',
                COALESCE(NEW.category, '')
            ),
            'B'
        )

        ||

        setweight(
            to_tsvector(
                'english',
                COALESCE(
                    array_to_string(
                        NEW.tags,
                        ' '
                    ),
                    ''
                )
            ),
            'C'
        )

        ||

        setweight(
            to_tsvector(
                'english',
                COALESCE(NEW.description, '')
            ),
            'D'
        );

    RETURN NEW;

END;
$$;
```

This function does not run because the application explicitly calls it.

It is executed automatically by a PostgreSQL trigger.

---

# 6. Understanding `NEW`

Inside a row-level trigger:

```sql
NEW
```

represents the new version of the row PostgreSQL is about to write.

For example, suppose an application performs:

```sql
INSERT INTO products (
    name,
    brand,
    category,
    tags,
    description,
    price,
    stock
)
VALUES (
    'Mechanical Gaming Keyboard',
    'Logitech',
    'Keyboards',
    ARRAY['gaming', 'mechanical', 'rgb'],
    'Compact keyboard designed for competitive gaming.',
    129.99,
    20
);
```

Inside the trigger:

```text
NEW.name
→ Mechanical Gaming Keyboard

NEW.brand
→ Logitech

NEW.category
→ Keyboards

NEW.tags
→ {gaming, mechanical, rgb}

NEW.description
→ Compact keyboard designed for competitive gaming.
```

The trigger uses these values to construct:

```text
NEW.search_vector
```

before PostgreSQL stores the row.

---

# 7. The Weighted Vector Inside the Trigger

The trigger preserves exactly the same V2 field weights.

## Name

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(NEW.name, '')
    ),
    'A'
)
```

The product name receives:

```text
Weight A
```

because a match in the name is considered highly relevant.

---

## Brand

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(NEW.brand, '')
    ),
    'B'
)
```

Brand receives:

```text
Weight B
```

---

## Category

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(NEW.category, '')
    ),
    'B'
)
```

Category also receives:

```text
Weight B
```

---

## Tags

The tags column is:

```sql
TEXT[]
```

Therefore it must first be converted into normal text:

```sql
array_to_string(
    NEW.tags,
    ' '
)
```

For example:

```text
{"gaming", "mechanical", "rgb"}
```

becomes:

```text
gaming mechanical rgb
```

The complete expression is:

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(
            array_to_string(
                NEW.tags,
                ' '
            ),
            ''
        )
    ),
    'C'
)
```

Tags receive:

```text
Weight C
```

---

## Description

```sql
setweight(
    to_tsvector(
        'english',
        COALESCE(NEW.description, '')
    ),
    'D'
)
```

Description receives:

```text
Weight D
```

A description match remains searchable but contributes less strongly to ranking than a product-name match.

---

# 8. Combining the Vectors

The `||` operator combines multiple `tsvector` values.

Conceptually:

```text
name vector        A
       \
brand vector       B
        \
category vector    B
          ─────────────→ search_vector
tags vector        C
        /
description        D
       /
```

A resulting vector may conceptually resemble:

```text
'game':2A,15D
'keyboard':3A,7B
'logitech':4B
'mechan':6C
'rgb':8C
'competit':14D
```

The weights remain embedded in the stored vector.

---

# 9. Attach the Trigger to `products`

Creating the function alone does nothing.

The function must be attached to the table:

```sql
CREATE TRIGGER products_search_vector_trigger

BEFORE INSERT OR UPDATE OF
    name,
    brand,
    category,
    tags,
    description

ON products

FOR EACH ROW

EXECUTE FUNCTION update_product_search_vector();
```

This is the mechanism that automatically calls the function.

---

# 10. `BEFORE INSERT`

The trigger uses:

```sql
BEFORE INSERT
```

because the vector should exist before the new product row is written.

Conceptually:

```text
Application INSERT
       ↓
PostgreSQL receives row
       ↓
BEFORE INSERT trigger
       ↓
NEW.search_vector calculated
       ↓
row written
```

The application does not need to provide `search_vector`.

---

# 11. `BEFORE UPDATE`

The trigger also runs when searchable product data changes.

For example:

```sql
UPDATE products
SET name = 'Wireless Mechanical Gaming Keyboard'
WHERE id = 42;
```

The flow becomes:

```text
UPDATE
  ↓
BEFORE UPDATE trigger
  ↓
recalculate search_vector
  ↓
store updated product
```

Therefore the stored vector remains synchronized with the product.

---

# 12. Why `UPDATE OF` Specific Columns?

The trigger is defined as:

```sql
UPDATE OF
    name,
    brand,
    category,
    tags,
    description
```

instead of simply:

```sql
UPDATE
```

because these are the only fields used in the FTS vector.

For example:

```sql
UPDATE products
SET stock = 15
WHERE id = 42;
```

does not change search semantics.

There is no reason to rebuild:

```text
search_vector
```

for a stock-only update.

Likewise:

```text
price
rating
stock
```

do not participate in the FTS document.

So the trigger does not need to run because those fields changed.

---

# 13. `FOR EACH ROW`

The trigger uses:

```sql
FOR EACH ROW
```

because every product requires its own search vector.

If an operation modifies ten products, PostgreSQL executes the row-level trigger for the affected rows individually.

Conceptually:

```text
Product 1 update
    ↓
trigger

Product 2 update
    ↓
trigger

Product 3 update
    ↓
trigger
```

Each row receives a vector derived from its own values.

---

# 14. Existing Rows Need a Backfill

Adding the column:

```sql
ALTER TABLE products
ADD COLUMN search_vector tsvector;
```

does not automatically populate existing products.

Existing rows initially contain:

```text
search_vector = NULL
```

The trigger handles new inserts and relevant future updates.

The existing dataset therefore requires a one-time backfill.

---

Run:

```sql
UPDATE products

    setweight(
        to_tsvector(

    ||

            'english',
            COALESCE(brand, '')
        ),
        'B'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(category, '')
        ),
        'B'
    )

    ||

    setweight(
        to_tsvector(
            'english',
            COALESCE(
```

For approximately 100,000 products:

```text
100,000 existing products
        ↓
calculate vectors once

```

This work should not need to occur again during every search.

# 18. Why Put This Logic in PostgreSQL?

An alternative would be:

```text
Python receives product
    ↓
Python calculates search data
    ↓
Python writes product
    ↓
Python separately writes search_vector
```

That would create synchronization risk.

For example:

```text
product updated
but
search_vector update forgotten
```

would leave stale search data.

Keeping this behavior in PostgreSQL gives the database responsibility for maintaining its own search representation.

The application can perform:

```sql
UPDATE products
SET description = ...
```

without knowing how `search_vector` is implemented.

---

# 19. Write Path vs Read Path

This is an important architectural change.

## V2

The expensive linguistic conversion occurs primarily during reads:

```text
SEARCH
  ↓
construct vectors
  ↓
match
```

## V3

The product vector is constructed during writes:

```text
INSERT / UPDATE
      ↓
trigger
      ↓
construct vector
      ↓
store it
```

Then search becomes:

```text
SEARCH
   ↓
use existing vector
```

This is a classic systems tradeoff:

```text
more work during writes
        ↓
less repeated work during reads
```

For a search-heavy application, this can be a very useful trade.

---

# 20. Create the GIN Index

After the search vectors have been populated:

```sql
CREATE INDEX idx_products_search_vector

ON products

USING GIN (search_vector);
```

The column contains the searchable document.

The GIN index provides an efficient inverted lookup structure over that document.

---

# 21. What GIN Means

GIN stands for:

```text
Generalized Inverted Index
```

A normal product-centric representation looks conceptually like:

```text
Product 1
    → gaming
    → keyboard
    → mechanical

Product 2
    → office
    → keyboard
    → wireless
```

An inverted representation reverses the relationship:

```text
gaming
    → Product 1
    → Product 8
    → Product 41

keyboard
    → Product 1
    → Product 2
    → Product 17

mechanical
    → Product 1
    → Product 22
```

This structure is much better suited to questions such as:

```text
Which products contain these search lexemes?
```

---

# 22. Run `ANALYZE`

After creating the column, populating the vectors and creating the index:

```sql
ANALYZE products;
```

This updates PostgreSQL's statistics for the table.

The query planner uses statistics when estimating whether strategies such as:

```text
Sequential Scan
Bitmap Scan
Index-assisted retrieval
```

are likely to be cheapest.

An index existing does not automatically mean PostgreSQL will choose it.

Planner statistics matter.

# 25. V3 Search Query

After all of that setup, the actual search query becomes significantly simpler than V2.

```sql
WITH search_input AS (

    SELECT websearch_to_tsquery(
        'english',
        %s
    ) AS query

)

SELECT
    p.id,
    p.name,
    p.description,
    p.brand,
    p.category,
    p.tags,
    p.price,
    p.rating,
    p.stock,
    p.created_at,

    ts_rank_cd(
        p.search_vector,
        q.query
    ) AS rank,

    ts_headline(
        'english',
        COALESCE(p.description, ''),
        q.query,
        'StartSel=<mark>, StopSel=</mark>, MaxWords=30, MinWords=10'
    ) AS headline

FROM products AS p

CROSS JOIN search_input AS q

WHERE p.search_vector @@ q.query

ORDER BY
    rank DESC,
    p.id ASC;
```

There is no longer a:

```sql
searchable_products AS (...)
```

CTE constructing vectors for the complete table.

The search directly references:

```sql
p.search_vector
```

---

# 26. What the GIN Index Optimizes

The important predicate is:

```sql
WHERE p.search_vector @@ q.query
```

GIN helps PostgreSQL determine which rows satisfy this full-text condition.

Conceptually:

```text
tsquery
   ↓
GIN inverted index
   ↓
candidate row locations
   ↓
retrieve matching products
```

This is fundamentally different from V2's query-time table-wide vector construction.

---

# 27. Expected V2 Execution Plan

V2 may look conceptually like:

```text
Sequential Scan
       ↓
construct tsvector
       ↓
apply @@ filter
       ↓
rank matches
       ↓
sort
```

The execution plan may contain:

```text
Seq Scan
```

and:

```text
Rows Removed by Filter
```

because PostgreSQL inspected rows and rejected non-matches.

---

# 28. Expected V3 Execution Plan

For sufficiently selective queries, V3 may produce:

```text
Bitmap Index Scan
        ↓
Bitmap Heap Scan
        ↓
calculate rank
        ↓
Sort
```

The raw plan may show:

```text
Bitmap Index Scan
```

with:

```text
Index Name:
idx_products_search_vector
```

This is strong evidence that the GIN index participated in candidate retrieval.

---

# 29. Bitmap Index Scan

A:

```text
Bitmap Index Scan
```

means PostgreSQL uses the index to determine candidate row locations.

Conceptually:

```text
GIN
 ↓
row 17
row 921
row 1408
row 2091
...
```

It does not necessarily retrieve complete product records during this step.

---

# 30. Bitmap Heap Scan

After identifying candidate row locations, PostgreSQL may perform:

```text
Bitmap Heap Scan
```

The heap is the actual table storage containing the product rows.

Therefore:

```text
Bitmap Index Scan
        ↓
find locations

Bitmap Heap Scan
        ↓
retrieve rows
```

These two plan nodes cooperate.

A bitmap plan is still an **index-assisted execution plan**.

---

# 31. GIN Does Not Guarantee Index Usage

The presence of:

```text
idx_products_search_vector
```

does not force PostgreSQL to use it.

The query planner may choose:

```text
Seq Scan
```

when it estimates that scanning the table will be cheaper.

For example, suppose:

```text
100,000 total products
90,000 products match
```

Using an index to locate almost every row may provide little benefit.

The planner could reasonably choose a sequential scan instead.

Therefore:

```text
Index exists
```

does not imply:

```text
Index must appear in every execution plan
```

---

# 32. Query Selectivity

A query is highly selective when it matches relatively few rows.

For example:

```text
"ergonomic mechanical gaming keyboard"
```

might match:

```text
120 / 100,000 products
```

A GIN index may be extremely useful.

A broad query such as:

```text
wireless
```

could match:

```text
30,000 / 100,000 products
```

The performance advantage may be smaller.

A meaningful benchmark should therefore test different levels of selectivity.

---

# 33. Matching and Ranking Remain Separate

GIN primarily helps with:

```sql
p.search_vector @@ q.query
```

which answers:

```text
Which products match?
```

Ranking still uses:

```sql
ts_rank_cd(
    p.search_vector,
    q.query
)
```

which answers:

```text
Among those matching products,
which should appear first?
```

These are different operations.

---

# 34. Why V3 Can Still Have a `Sort`

GIN does not normally return rows already ordered by:

```sql
ts_rank_cd()
```

Therefore PostgreSQL can still execute:

```text
GIN lookup
    ↓
matching products
    ↓
calculate ts_rank_cd()
    ↓
Sort
    ↓
results
```

Seeing:

```text
Sort
```

in V3 does not mean indexing failed.

The index optimized candidate retrieval.

Ranking and ordering remain separate work.

---

# 35. `ts_headline()` Still Has a Cost

V3 still uses:

```sql
ts_headline()
```

to produce contextual result snippets.

For example:

```html
Premium <mark>mechanical keyboard</mark>
for competitive players...
```

GIN does not eliminate this work.

The function still has to process the returned product descriptions.

Therefore V3 optimizes one major search stage:

```text
candidate retrieval
```

but does not magically eliminate every computational cost in the endpoint.

---

# 36. Write Cost

V3 improves repeated search reads at the cost of additional write work.

An insert becomes:

```text
INSERT product
      ↓
trigger
      ↓
build tsvector
      ↓
store vector
      ↓
update GIN index
```

An update to a searchable field becomes:

```text
UPDATE description
       ↓
trigger
       ↓
rebuild vector
       ↓
update stored row
       ↓
maintain GIN
```

So indexing is not free.

---

# 37. Storage Cost

V3 adds storage for:

```text
search_vector
```

and:

```text
GIN index
```

The database therefore consumes more disk space than V2.

The tradeoff is:

```text
more storage
+
more write work
        ↓
less repeated search-time computation
+
potentially much faster candidate lookup
```

---

# 38. Trigger Cost

The trigger itself introduces work during:

```text
INSERT
UPDATE searchable fields
```

However, it does not execute during ordinary search queries.

That distinction matters:

```text
WRITE PATH
    ↓
trigger runs

SEARCH PATH
    ↓
trigger does not run
```

The search simply reads:

```sql
p.search_vector
```

# 46. Why the Trigger Is Important

Without the trigger, a persisted vector creates a dangerous possibility:

```text
product says:
"Wireless Mechanical Keyboard"

search_vector still represents:
"Wired Office Keyboard"
```

The product and its searchable representation would disagree.

The trigger establishes an invariant:

```text
Whenever searchable product fields change,
search_vector is rebuilt before the row is stored.
```

That database-level guarantee is more reliable than depending on every application code path to remember the update.

V3 introduces several new database concepts:


The most important systems lesson is:


V2 performs repeated work during searches.

V3 moves vector generation toward writes and maintains an inverted index so searches can avoid much of that repeated work.

# 49. V3 Summary

V3 consists of four major database changes:

```text
1. Persist search_vector

2. Maintain it automatically with a trigger

3. Backfill existing products

4. Create a GIN inverted index
```

The final architecture is:

```text
                 PRODUCTS
                    │
        searchable field changes
                    │
                    ▼
        BEFORE INSERT / UPDATE
                 trigger
                    │
                    ▼
       update_product_search_vector()
                    │
                    ▼
          persisted tsvector
                    │
                    ▼
               GIN index


SEARCH QUERY
     │
     ▼
websearch_to_tsquery()
     │
     ▼
     GIN
     │
     ▼
candidate products
     │
     ▼
search_vector @@ query
     │
     ▼
ts_rank_cd()
     │
     ▼
Sort
     │
     ▼
Results
```

In one sentence:

```text
V2 builds linguistic representations while searching.

V3 maintains those representations ahead of time
and indexes them for efficient retrieval.
```
