# how it works under the hood 

Suppose we have:

name = "Logitech Wireless Gaming Keyboard"

and pattern:

%wireless%

Conceptually PostgreSQL checks:

Logitech Wireless Gaming Keyboard
         ^^^^^^^^

and asks:

Does this string satisfy the pattern?

Yes.

It is string pattern matching.

This distinction matters enormously.

ILIKE is not understanding words.

It is not a search engine in the linguistic sense.



9. First major limitation: no stemming

Suppose product description contains:

Designed for runners

Search:

ILIKE '%running%'

Does:

running

mean the same thing as:

runner
run
runs

to ILIKE?

No.

It sees characters.

Not language.

run
runner
running

are simply different strings.

Later PostgreSQL full-text search gives us lexemes/stemming.

That's one reason V2 exists.

10. Second huge problem: multi-word search

This one is important.

Product:

Logitech Wireless Mechanical Keyboard

User searches:

wireless keyboard

Your V1 pattern becomes:

%wireless keyboard%

Now look at the actual product:

Wireless Mechanical Keyboard

Is the exact substring:

wireless keyboard

present?

No.

There's:

mechanical

between them.

Therefore:

name ILIKE '%wireless keyboard%'

does not match:

Logitech Wireless Mechanical Keyboard

even though a human immediately knows it's highly relevant.

🔥 This is one of the first places where naive substring search breaks.

11. Another problem: ranking

Imagine these products:

1. Apple MacBook Air M5

2. Protective Laptop Sleeve
   Description:
   "Compatible with Apple MacBook Air M5"

3. Apple USB-C Charger
   Description:
   "Works with MacBook Air"

Search:

macbook air

With:

WHERE
    name ILIKE '%macbook air%'
    OR description ILIKE '%macbook air%'

they all match.

But which should be first?

Obviously:

Apple MacBook Air M5

should probably rank above:

Protective Laptop Sleeve

Yet ILIKE itself says only:

match ✅
no match ❌

It doesn't naturally give you:

Product A = 0.93 relevance
Product B = 0.61 relevance
Product C = 0.42 relevance

That's another reason we eventually need ranking.

12. The performance problem

And this is where the project gets interesting.

Consider:

WHERE name ILIKE '%keyboard%'

Notice the leading:

%

PostgreSQL doesn't know where the match begins.

Could be:

keyboard...

or:

gaming keyboard...

or:

logitech wireless keyboard...

or:

case for keyboard...

So PostgreSQL may have to inspect a huge number of rows.

With 100,000 products, conceptually:

row 1 → inspect name
row 2 → inspect name
row 3 → inspect name
...
row 100,000 → inspect name

That's often a:

Seq Scan

or sequential scan.

Meaning:

Scan through the table looking at rows.

13. This is why we intentionally created 100k rows

With:

100 rows

you might get:

0.4 ms

and conclude:

damn ILIKE is fast 🔥

No.

Your database is just tiny 😂.

With:

100,000+

we can start examining real query-planner behavior.

That's why the data volume matters.

15. WTF is ~~*?

You may see PostgreSQL display:

name ~~* '%keyboard%'

instead of:

name ILIKE '%keyboard%'

That's normal.

Internally PostgreSQL has operator representations:

LIKE   → ~~
ILIKE  → ~~*

You don't normally write:

name ~~* '%keyboard%'

Use:

name ILIKE '%keyboard%'

But EXPLAIN may show its internal operator form.

16. Why ordinary B-tree indexes don't magically fix %query%

Suppose you create:

CREATE INDEX idx_products_name
ON products(name);

You might expect:

search = fast now 🚀

But:

name ILIKE '%keyboard%'

has a leading wildcard.

A traditional ordered index can't efficiently jump to:

keyboard

because it doesn't know where inside each string the substring occurs.

Think of a dictionary.

A dictionary is excellent for:

words STARTING WITH "key"

because everything is alphabetically ordered.

But suppose I ask:

Find every dictionary word containing "key" anywhere.

Now alphabetical ordering is much less useful.

You potentially have to inspect tons of words.

Same basic intuition.

Later:

pg_trgm + GIN

can solve substring/fuzzy lookup differently.

But don't touch that yet.

We need to feel the pain first.

17. Prefix searches are different

Compare:

ILIKE 'key%'

versus:

ILIKE '%key%'

First:

key...

means:

value begins with key

Database indexing has much more opportunity here.

Second:

...key...

means:

key could occur anywhere

Much harder.

This distinction comes back when we build autocomplete.

Autocomplete often wants:

mac
→ macbook
→ macbook air
→ mac mini

which is naturally closer to prefix matching.
