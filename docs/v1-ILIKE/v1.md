# V1 — PostgreSQL `ILIKE` Search

## Goal

V1 is the intentionally simple baseline for SearchLab.

The search engine does **case-insensitive substring matching** across a few product columns using PostgreSQL `ILIKE`.

It does **not** understand language, rank results, handle typos, stem words, or use a dedicated search index.

That is intentional.

V1 gives us a naive baseline that later versions can improve and benchmark against.

---

# 1. `LIKE` vs `ILIKE`

PostgreSQL provides pattern matching with `LIKE` and `ILIKE`.

```sql
LIKE
```

is case-sensitive.

```sql
ILIKE
```

is case-insensitive.

Example:

```sql
SELECT name
FROM products
WHERE name ILIKE '%keyboard%';
```

This can match values such as:

```text
Keyboard
KEYBOARD
Gaming Keyboard
wireless keyboard
```

For a user-facing search box, `ILIKE` is usually more convenient than `LIKE` for a simple baseline because users generally do not expect capitalization to matter.

---

# 2. Wildcards: `%` and `_`

PostgreSQL pattern matching gives us two important wildcard characters.

## `%`

`%` means:

> zero or more characters

Examples:

```sql
ILIKE 'apple%'
```

Starts with `apple`.

```text
Apple
Apple MacBook
Apple Watch
```

---

```sql
ILIKE '%apple'
```

Ends with `apple`.

---

```sql
ILIKE '%apple%'
```

Contains `apple` anywhere.

---

## `_`

`_` means:

> exactly one character

Example:

```sql
ILIKE 'M_cBook'
```

could match:

```text
MacBook
MecBook
MicBook
```

because `_` represents exactly one character.

# 4. Searching multiple columns

A user searching:

```text
sony
```

may be referring to text stored in:

- `name`
- `description`
- `brand`
- `category`

So V1 searches all four columns:

```sql
SELECT
    id,
    name,
    description,
    brand,
    category,
    price,
    rating,
    stock
FROM products
WHERE
    name ILIKE '%sony%'
    OR description ILIKE '%sony%'
    OR brand ILIKE '%sony%'
    OR category ILIKE '%sony%';
```

Conceptually PostgreSQL evaluates each candidate row:

```text
Does name match?
OR does description match?
OR does brand match?
OR does category match?
```

If any condition is true, the row qualifies.

---

# 5. Never hardcode user input into SQL

The query must be parameterized.

## Correct

```python
query = "sony"
pattern = f"%{query}%"

cursor.execute(
    """
    SELECT
        id,
        name,
        description,
        brand,
        category,
        price,
        rating,
        stock
    FROM products
    WHERE
        name ILIKE %s
        OR description ILIKE %s
        OR brand ILIKE %s
        OR category ILIKE %s
    LIMIT 10
    """,
    (
        pattern,
        pattern,
        pattern,
        pattern,
    ),
)
```

The `%s` placeholders are handled by Psycopg.

## Do not do this

```python
sql = f"""
SELECT *
FROM products
WHERE name ILIKE '%{query}%'
"""
```

Directly interpolating user input into SQL is unsafe and can create SQL-injection vulnerabilities.

Parameterization protects the SQL structure from user input.

> Note: parameterization does not make `%` and `_` stop behaving as `ILIKE` wildcards. That is a separate search-semantics issue.

---

# 6. How `ILIKE` works conceptually

Suppose the stored value is:

```text
Logitech Wireless Gaming Keyboard
```

and the pattern is:

```text
%wireless%
```

PostgreSQL checks whether that string satisfies the pattern.

Conceptually:

```text
Logitech Wireless Gaming Keyboard
         ^^^^^^^^
```

It matches.

But this is still only **string pattern matching**.

`ILIKE` does not understand words or meaning.

---

# 7. Limitation: no stemming

Suppose a description contains:

```text
Designed for runners
```

and the user searches:

```text
running
```

V1 effectively asks:

```sql
ILIKE '%running%'
```

To `ILIKE`, these are different strings:

```text
run
runner
running
runs
```

It does not understand that they share a linguistic root.

Later PostgreSQL Full-Text Search will introduce tokenization and lexemes/stemming.

That is one reason V2 exists.

---

# 8. Limitation: multi-word search

Suppose the product name is:

```text
Logitech Wireless Mechanical Keyboard
```

and the user searches:

```text
wireless keyboard
```

V1 creates:

```text
%wireless keyboard%
```

and executes:

```sql
name ILIKE '%wireless keyboard%'
```

But this exact contiguous substring does not appear in:

```text
Wireless Mechanical Keyboard
```

because `Mechanical` is between the two words.

So V1 may return no match even though a human knows the product is highly relevant.

This is a major weakness of naive substring search.

---

# 9. Limitation: no relevance ranking

Imagine:

```text
1. Apple MacBook Air M5

2. Protective Laptop Sleeve
   Description: "Compatible with Apple MacBook Air M5"

3. Apple USB-C Charger
   Description: "Works with MacBook Air"
```

The user searches:

```text
macbook air
```

Several rows may match.

But `ILIKE` only naturally tells us:

```text
match
no match
```

It does not naturally produce relevance scores such as:

```text
MacBook Air          0.93
Laptop Sleeve        0.61
USB-C Charger        0.42
```

Without an explicit `ORDER BY`, PostgreSQL also does not guarantee a meaningful relevance order.

Ranking is introduced later.

---

# 10. Performance problem

Consider:

```sql
WHERE name ILIKE '%keyboard%'
```

The leading `%` means the match can begin anywhere:

```text
keyboard...
gaming keyboard...
logitech wireless keyboard...
case for keyboard...
```

A normal ordered lookup cannot simply jump to one known prefix.

PostgreSQL may therefore inspect many rows and often choose a:

```text
Seq Scan
```

or sequential scan.

Conceptually:

```text
row 1       inspect
row 2       inspect
row 3       inspect
...
row 100000  inspect
```

The exact amount of work depends on the query, the planner, the `LIMIT`, data distribution, cache state, and available indexes.

---

# 11. Why the dataset has 100,000 rows

Performance problems are difficult to observe with tiny datasets.

With only 100 rows, a naive query may complete so quickly that every design appears fast.

With 100,000 products, we can start observing:

- scan strategies
- rows filtered
- buffer activity
- planning time
- execution time
- the effect of indexes
- differences between search architectures

The dataset exists to make database behavior visible.

# 12. `EXPLAIN ANALYZE`

To inspect how PostgreSQL actually executes a query:

```sql
EXPLAIN ANALYZE
SELECT *
FROM products
WHERE name ILIKE '%keyboard%';
```

You may see output similar to:

```text
Seq Scan on products
  Filter: (name ~~* '%keyboard%'::text)
  Rows Removed by Filter: ...

Planning Time: ...
Execution Time: ...
```

The important first observation is often:

```text
Seq Scan on products
```

That tells us PostgreSQL chose to scan rows rather than use an index lookup for this search.

---

# 13. `EXPLAIN (ANALYZE, BUFFERS)`

SearchLab uses:

```sql
EXPLAIN (
    ANALYZE,
    BUFFERS,
    FORMAT JSON
)
SELECT ...
```

Each option has a purpose.

## `EXPLAIN`

Shows the execution plan selected by the PostgreSQL planner.

## `ANALYZE`

Actually executes the query and records real runtime statistics.

This is important:

> `EXPLAIN ANALYZE` is not only describing the query. It runs it.

For `SELECT` queries that is normally fine.

## `BUFFERS`

Shows PostgreSQL buffer activity such as:

```text
Shared Hit Blocks
Shared Read Blocks
```

A shared hit means the required block was already available in PostgreSQL's shared-buffer cache.

A shared read means a block had to be read into shared buffers.

## `FORMAT JSON`

Returns the plan as structured data rather than human-readable text.

That makes it easy for the SearchLab frontend to display fields such as:

```text
Node Type
Planning Time
Execution Time
Actual Rows
Rows Removed by Filter
Shared Hit Blocks
Shared Read Blocks
```

---

# 14. Why PostgreSQL shows `~~*`

An `EXPLAIN` plan may display:

```text
name ~~* '%keyboard%'
```

instead of:

```sql
name ILIKE '%keyboard%'
```

That is normal.

PostgreSQL internally represents:

```text
LIKE   → ~~
ILIKE  → ~~*
```

Application SQL should still use the readable form:

```sql
ILIKE
```

---

# 15. Why an ordinary B-tree does not magically fix `%query%`

Suppose we create:

```sql
CREATE INDEX idx_products_name
ON products(name);
```

A common mistake is to assume:

```text
index exists → every search is fast
```

But:

```sql
name ILIKE '%keyboard%'
```

contains a leading wildcard.

An ordinary ordered index is naturally much more useful when the database can reason from the beginning of a value.

Think of a dictionary.

Finding:

```text
words beginning with "key"
```

fits alphabetical ordering well.

Finding:

```text
every word containing "key" anywhere
```

does not.

Later we will study search-specific indexing such as PostgreSQL trigram indexes for substring/fuzzy matching.

---

# 16. Prefix search is different

Compare:

```sql
ILIKE 'key%'
```

with:

```sql
ILIKE '%key%'
```

The first means:

```text
starts with key
```

The second means:

```text
contains key anywhere
```

Prefix search gives the database more structural information than arbitrary substring search.

The exact indexability of case-insensitive prefix search depends on index definition, collation, and operator strategy, so we should verify it with `EXPLAIN` rather than assuming a B-tree will always be used.

This distinction becomes important when we build autocomplete.

---

# 17. What about `tags TEXT[]`?

`tags` is an array, not a text value.

So this is not valid:

```sql
tags ILIKE '%wireless%'
```

because `ILIKE` expects text operands.

We could force the array into text:

```sql
array_to_string(tags, ' ') ILIKE '%wireless%'
```

but V1 intentionally avoids that.

For the baseline, we search:

```text
name
description
brand
category
```

We will handle tags more deliberately later.

# 19. Python implementation

File:

```text
backend/src/advanced_search_system/search/v1/search.py
```

```python
from time import perf_counter
import tracemalloc

from advanced_search_system.db.connection import get_connection


def search_products(query: str):
    pattern = f"%{query}%"

    sql = """
    SELECT
        id,
        name,
        description,
        brand,
        category,
        price,
        rating,
        stock
    FROM products
    WHERE
        name ILIKE %s
        OR description ILIKE %s
        OR brand ILIKE %s
        OR category ILIKE %s
    LIMIT 10;
    """

    params = (
        pattern,
        pattern,
        pattern,
        pattern,
    )

    # ------------------------------------------
    # APPLICATION-SIDE MEASUREMENTS
    # ------------------------------------------

    tracemalloc.start()

    start_timer = perf_counter()

    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(sql, params)
            rows = cur.fetchall()

    end_timer = perf_counter()

    current_memory, peak_memory = (
        tracemalloc.get_traced_memory()
    )

    tracemalloc.stop()

    execution_time_ms = (
        end_timer - start_timer
    ) * 1000

    current_memory_mb = (
        current_memory / (1024 * 1024)
    )

    peak_memory_mb = (
        peak_memory / (1024 * 1024)
    )

    # ------------------------------------------
    # POSTGRESQL EXECUTION PLAN
    # ------------------------------------------

    explain_sql = f"""
    EXPLAIN (
        ANALYZE,
        BUFFERS,
        FORMAT JSON
    )
    {sql}
    """

    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                explain_sql,
                params,
            )

            explain_row = cur.fetchone()

    query_plan = None

    if explain_row:
        explain_data = explain_row["QUERY PLAN"]

        if explain_data:
            query_plan = explain_data[0]

    # ------------------------------------------
    # RESPONSE
    # ------------------------------------------

    return {
        "query": query,
        "count": len(rows),

        "metrics": {
            "execution_time_ms": round(
                execution_time_ms,
                3,
            ),
            "current_memory_mb": round(
                current_memory_mb,
                3,
            ),
            "peak_memory_mb": round(
                peak_memory_mb,
                3,
            ),
        },

        "query_plan": query_plan,
        "results": rows,
    }
```

This implementation assumes the database connection is configured with Psycopg's `dict_row`, so:

```python
cur.fetchall()
```

returns dictionaries such as:

```python
{
    "id": 42,
    "name": "Logitech Wireless Keyboard",
    "brand": "Logitech",
}
```

and the `EXPLAIN` row can be accessed using:

```python
explain_row["QUERY PLAN"]
```

# 20. What the measurements mean

V1 currently uses three different measurement sources.

## `perf_counter()`

```python
start_timer = perf_counter()
...
end_timer = perf_counter()
```

This measures elapsed application-side wall-clock time.

In the current implementation it includes roughly:

```text
opening the database connection
executing the SELECT
transferring/fetching rows
Psycopg converting result values
connection cleanup
```

So:

```text
execution_time_ms
```

is better understood as **application-observed database operation latency**, not pure PostgreSQL execution time.

---

## `tracemalloc`

```python
tracemalloc.start()
...
current_memory, peak_memory = tracemalloc.get_traced_memory()
```

This measures Python allocations tracked by `tracemalloc`.

It does **not** measure PostgreSQL server RAM.

The UI displays:

```text
Python current memory
Python peak memory
```

These are Python-side diagnostics only.

---

## `EXPLAIN ANALYZE`

PostgreSQL's JSON plan provides database-side metrics such as:

```text
Planning Time
Execution Time
Node Type
Actual Rows
Rows Removed by Filter
Shared Hit Blocks
Shared Read Blocks
```

These should remain conceptually separate from Python's `perf_counter()` result.

For example:

```text
Python/application latency      145.2 ms
PostgreSQL execution              4.8 ms
PostgreSQL planning               0.3 ms
```

Those numbers are not contradictory.

The application measurement includes work PostgreSQL's execution timer does not.

# 24. Important benchmark caveat: `LIMIT 10`

V1 uses:

```sql
LIMIT 10
```

That means PostgreSQL may stop scanning once it finds ten matches.

For a common query such as:

```text
keyboard
```

it may inspect only a small part of the table before satisfying the limit.

So a `Seq Scan` does **not** automatically mean PostgreSQL inspected all 100,000 rows.

To study the behavior more carefully, test several query types.

## Common result

```text
keyboard
```

## Rare result

Use a term that appears only occasionally.

## No result

```text
qzxneverexists92847
```

For a nonexistent substring, PostgreSQL cannot stop because it found ten matches.

That often exposes the full cost of the scan more clearly.

# 26. Questions V1 should answer

Before moving to V2, be able to explain:

### What does `%` mean?

Zero or more characters.

### What does `_` mean?

Exactly one character.

### What is the difference between `LIKE` and `ILIKE`?

`LIKE` is case-sensitive; PostgreSQL `ILIKE` performs case-insensitive pattern matching.

### Why can `wireless keyboard` fail to match `wireless mechanical keyboard`?

Because `%wireless keyboard%` requires the words to occur as one contiguous substring.

### What is a sequential scan?

PostgreSQL reads table rows/pages and checks the filter rather than locating candidates through an appropriate index access path.

### Why is `%keyboard%` harder to optimize with an ordinary ordered index than `keyboard%`?

The leading wildcard means the match may begin anywhere in the string, so the database cannot narrow the search using the beginning of the stored value in the same way.

### What does `Rows Removed by Filter` mean?

Rows processed by that plan node that failed its filter condition.

### What is the difference between Python latency and PostgreSQL execution time?

Python's timer measures application-observed elapsed time around the database operation. PostgreSQL's `Execution Time` measures database-side execution reported by `EXPLAIN ANALYZE`.

### What does `tracemalloc` measure?

Tracked Python memory allocations, not PostgreSQL server memory.

# 27. What V1 deliberately does not solve

V1 has no:

- stemming
- tokenization
- linguistic understanding
- relevance ranking
- typo tolerance
- fuzzy search
- search-specific GIN index
- autocomplete
- facets
- cursor pagination
- Redis caching
- query analytics

That is not failure.

Those limitations are the experiment.

The purpose of V1 is:

> Build the simplest correct search, measure it, understand where it breaks, then evolve the architecture deliberately.
