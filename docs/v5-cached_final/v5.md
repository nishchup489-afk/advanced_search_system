# V5 — Redis Search Result Caching

## Redis + FTS + GIN + Fuzzy Fallback

V5 is the final version of the SearchLab architecture.

The previous versions progressively improved how PostgreSQL understands, retrieves and recovers search queries:

```text
V1
ILIKE substring search

        ↓

V2
PostgreSQL Full-Text Search

        ↓

V3
Persisted tsvector
+ trigger maintenance
+ GIN indexing

        ↓

V4
FTS primary retrieval
+ pg_trgm fuzzy fallback

        ↓

V5
Redis result caching
+ complete V4 search pipeline
```

V5 does not introduce a new search algorithm.

Instead, it asks a different systems question:

```text
If we have already computed the answer
to this search recently,
why should PostgreSQL compute it again?
```

Redis provides a fast in-memory cache in front of the search pipeline.

---

# 1. V5 Goal

The purpose of V5 is:

```text
avoid repeated database work
for repeated search requests
```

Suppose a user searches:

```text
mechanical keyboard
```

Without caching:

```text
request 1
    ↓
PostgreSQL search

request 2
    ↓
PostgreSQL search again

request 3
    ↓
PostgreSQL search again
```

Even if the underlying search result has not changed, the database performs the work repeatedly.

V5 changes that.

```text
request 1
    ↓
Redis MISS
    ↓
PostgreSQL
    ↓
Redis stores result

request 2
    ↓
Redis HIT
    ↓
return cached result

request 3
    ↓
Redis HIT
    ↓
return cached result
```

The database is completely bypassed on a cache hit.

---

# 2. Final Search Architecture

The complete SearchLab pipeline becomes:

```text
                     SEARCH REQUEST
                           │
                           ▼
                    QUERY NORMALIZATION
                           │
                           ▼
                       CACHE KEY
                           │
                           ▼
                         REDIS
                           │
                  ┌────────┴────────┐
                  │                 │
                 HIT               MISS
                  │                 │
                  │                 ▼
                  │        FULL-TEXT SEARCH
                  │                 │
                  │                 ▼
                  │        persisted search_vector
                  │                 │
                  │                 ▼
                  │              GIN index
                  │                 │
                  │                 ▼
                  │           FTS results?
                  │           ┌─────┴─────┐
                  │          YES          NO
                  │           │            │
                  │           │            ▼
                  │           │         pg_trgm
                  │           │            │
                  │           │      similarity()
                  │           │            │
                  │           └──────┬─────┘
                  │                  │
                  │                  ▼
                  │               results
                  │                  │
                  │                  ▼
                  │              Redis SET
                  │                + TTL
                  │                  │
                  └──────────┬───────┘
                             │
                             ▼
                          FastAPI
                             │
                             ▼
                            USER
```

This is now a multi-layer search system.

---

# 3. What Redis Is

Redis is an in-memory data store.

Unlike PostgreSQL, which primarily stores persistent relational data, Redis is commonly used for:

```text
caching
sessions
rate limiting
temporary state
queues
counters
distributed coordination
```

For SearchLab, Redis is used strictly as:

```text
a search-result cache
```

PostgreSQL remains the source of truth.

---

# 4. Redis Is Not the Search Engine

This distinction is critical.

Redis does not perform:

```text
tokenization
stemming
tsquery parsing
GIN FTS retrieval
ts_rank_cd()
trigram similarity
fuzzy ranking
```

Those responsibilities still belong to PostgreSQL.

Redis simply stores the result after PostgreSQL has already computed it.

Conceptually:

```text
PostgreSQL
    ↓
computes correct answer
    ↓
Redis remembers answer temporarily
```

Therefore:

```text
Redis
≠
search engine
```

For this architecture:

```text
PostgreSQL
=
search engine

Redis
=
cache
```

---

# 5. Why Cache Search Results?

Search queries can be expensive.

A request may involve:

```text
network communication
database planning
GIN lookup
heap access
ranking
sorting
ts_headline()
fuzzy fallback
row serialization
result transfer
```

If the exact same logical query is repeated shortly afterward, repeating all of that work may be unnecessary.

Caching converts:

```text
repeat expensive computation
```

into:

```text
retrieve previously computed result
```

```text
redis-py
```

as the Python Redis client.

Installation:

```bash
uv add redis
```

The Redis client is intended to be reused rather than reconstructed for every request.

A typical project structure is:

```text
advanced_search_system/
├── cache/
│   ├── __init__.py
│   └── client.py
│
├── db/
├── search/
├── config.py
└── main.py
```

# 7. Redis Configuration

Redis configuration belongs in application settings.

Example `.env`:

```env
REDIS_URL=redis://localhost:6379
```

The Pydantic settings model includes:

```python
redis_url: str = "redis://localhost:6379"
```

Then the Redis client can be created from that setting.

Example:

```python
import redis

from advanced_search_system.config import settings


redis_client = redis.from_url(
    settings.redis_url,
    decode_responses=True,
)
```

This gives the application one reusable Redis client.

---

# 8. Why Reuse the Redis Client?

A Redis client internally manages connections through a connection pool.

Therefore the desired architecture is:

```text
application starts
      ↓
Redis client created
      ↓
connection pool
      ↓
client reused across requests
```

rather than:

```text
request
 ↓
create Redis client

request
 ↓
create another Redis client

request
 ↓
create another Redis client
```

The Redis client is infrastructure that should generally be long-lived.

---

# 9. Query Normalization

Before creating a cache key, V5 normalizes the query.

Example implementation:

```python
def normalize_query(query: str) -> str:
    return " ".join(
        query.lower().split()
    )
```

This converts:

```text
"   Logitech    Keyboard   "
```

into:

```text
"logitech keyboard"
```

It also converts:

```text
"LOGITECH KEYBOARD"
```

into the same value:

```text
"logitech keyboard"
```

---

# 10. Why Normalize Before Caching?

Without normalization, these queries:

```text
Logitech Keyboard
logitech keyboard
LOGITECH KEYBOARD
logitech     keyboard
```

could produce four separate Redis keys.

But for the current search behavior, they are effectively equivalent requests.

Normalization increases the probability that equivalent queries share the same cached result.

Conceptually:

```text
many textual forms
        ↓
one normalized representation
        ↓
one cache key
```

---

# 11. Normalization Must Match Search Semantics

Cache normalization must be conservative.

If two queries can produce different results, they must not accidentally share the same key.

For the current system:

```text
lowercasing
whitespace normalization
```

are reasonable.

But aggressive normalization such as:

```text
removing operators
removing quotes
removing minus signs
rewriting words
```

could be dangerous.

For example:

```text
apple OR samsung
```

and:

```text
apple samsung
```

do not necessarily mean the same thing.

A cache key must preserve meaningful search semantics.

---

# 12. Cache Key

V5 generates a cache key from the normalized query.

A simple design could be:

```text
search:v5:logitech keyboard
```

The project uses a hashed form:

```python
query_hash = hashlib.sha256(
    normalized_query.encode("utf-8")
).hexdigest()
```

Then:

```python
cache_key = (
    f"search:v5:{query_hash}"
)
```

The final Redis key resembles:

```text
search:v5:
e2c9b4...
```

---

# 13. Why Hash the Query?

Hashing has several advantages.

It produces:

```text
fixed-length keys
```

regardless of query length.

It also avoids putting arbitrary user text directly into Redis key names.

Conceptually:

```text
"logitech keyboard"
        ↓
SHA-256
        ↓
search:v5:8f48...
```

The hash is not used for security here.

It is mainly a deterministic identifier for the normalized query.

---

# 14. Why Include `v5` in the Cache Key?

The prefix:

```text
search:v5:
```

is a cache namespace.

This is very important when the search algorithm changes.

Suppose an old implementation stored:

```text
search:v4:<hash>
```

Then V5 changes:

```text
ranking
filters
search behavior
result structure
```

If both versions used the same cache key, old results could leak into the new system.

Versioning provides isolation:

```text
search:v4:...
search:v5:...
```

The cache can evolve alongside the application.

---

# 15. Cache Lookup

The first major operation in V5 is:

```python
cached_value = redis_client.get(
    cache_key
)
```

There are two possible outcomes:

```text
value exists
→ CACHE HIT
```

or:

```text
value does not exist
→ CACHE MISS
```

This decision determines whether PostgreSQL needs to execute.

---

# 16. Cache Hit

A cache hit means Redis already contains a valid result for the query.

Pipeline:

```text
query
 ↓
normalize
 ↓
build key
 ↓
Redis GET
 ↓
HIT
 ↓
deserialize
 ↓
return
```

PostgreSQL is not touched.

Therefore:

```text
FTS executed       = false
fuzzy executed     = false
EXPLAIN executed   = false
database executed  = false
```

This is the defining optimization of V5.

---

# 17. Cache Miss

A cache miss means Redis does not currently contain the query result.

Pipeline:

```text
Redis GET
    ↓
MISS
    ↓
V4 search pipeline
    ↓
result
    ↓
Redis SET
    ↓
return
```

The entire search engine from previous versions still exists behind the cache.

---

# 18. V5 Does Not Replace V4

A common misunderstanding would be:

```text
V5 uses Redis instead of V4
```

That is incorrect.

The actual relationship is:

```text
V5
└── cache layer
    └── V4 search pipeline
        ├── V3 FTS
        └── fuzzy fallback
```

Redis wraps the existing search system.

It does not replace it.

---

# 19. Primary Search on Cache Miss

If Redis misses, V5 first executes the V3 full-text query.

Conceptually:

```text
normalized query
      ↓
websearch_to_tsquery()
      ↓
persisted search_vector
      ↓
GIN
      ↓
FTS matches
```

If matching rows exist:

```text
strategy = full_text
fallback_used = false
```

Those results become the response and cache payload.

---

# 20. Fuzzy Fallback on Cache Miss

If FTS produces zero results:

```text
FTS
 ↓
0 results
```

V5 continues into the V4 fuzzy fallback.

```text
pg_trgm
    ↓
% candidate filtering
    ↓
similarity()
    ↓
GREATEST()
    ↓
fuzzy_score
    ↓
results
```

Then:

```text
strategy = fuzzy_fallback
fallback_used = true
```

Those fuzzy results are cached exactly like normal FTS results.

---

# 21. What Gets Cached?

The cache should store stable search-result information.

For example:

```python
cache_payload = {
    "strategy": strategy,
    "fallback_used": fallback_used,
    "engine": engine,
    "count": len(results),
    "results": results,
}
```

This describes:

```text
what search strategy produced the result
and
what products were returned
```

---

# 22. What Should Not Be Cached?

V5 intentionally does not cache request-specific diagnostics such as:

```text
application timing
Python memory
EXPLAIN plan
Redis lookup time
Redis write time
PostgreSQL execution time
```

These values describe one execution.

They should not be reused as though they describe a later cache-hit request.

---

# 23. Why Not Cache `query_plan`?

Suppose the first request produces:

```text
Bitmap Index Scan
    ↓
Bitmap Heap Scan
```

and then the result is stored in Redis.

The second request is:

```text
Redis HIT
```

PostgreSQL does not execute at all.

If V5 returned the old cached query plan, the UI might imply:

```text
PostgreSQL used a Bitmap Index Scan
```

for the second request.

That would be false.

Therefore:

```text
cache hit
→ query_plan = null
```

because no database plan existed for that request.

---

# 24. Serialization

Redis stores strings or bytes.

Python search results can contain values such as:

```text
Decimal
datetime
lists
dictionaries
```

which are not always directly JSON serializable.

The backend therefore converts results into JSON-safe values.

Example:

```python
safe_results = jsonable_encoder(
    rows
)
```

Then:

```python
json.dumps(
    safe_results
)
```

can safely serialize the data for Redis.

---

# 25. Writing to Redis

After PostgreSQL produces the final result:

```python
redis_client.set(
    cache_key,
    json.dumps(cache_payload),
    ex=CACHE_TTL_SECONDS,
)
```

The important arguments are:

```text
key
value
expiration
```

For example:

```text
key:
search:v5:<hash>

value:
serialized search result

expiration:
300 seconds
```

---

# 26. TTL

TTL means:

```text
Time To Live
```

V5 uses a finite cache lifetime.

Example:

```python
CACHE_TTL_SECONDS = 300
```

which equals:

```text
5 minutes
```

After that time, Redis considers the key expired.

The next request becomes a cache miss.

---

# 27. Why Use a TTL?

Search results can become stale.

Suppose Redis caches:

```text
Mechanical Keyboard
price = $129.99
stock = 20
```

Then PostgreSQL changes:

```text
price = $99.99
stock = 0
```

Redis may temporarily still contain the old product representation.

A TTL limits how long stale cached results can survive.

Conceptually:

```text
cache created
    ↓
valid temporarily
    ↓
TTL expires
    ↓
next request recomputes from PostgreSQL
```

---

# 28. Cache Staleness

Cached data is not automatically guaranteed to represent the latest database state.

This creates a consistency tradeoff.

```text
long TTL
→ more cache hits
→ potentially more stale results

short TTL
→ fresher data
→ more PostgreSQL work
```

Choosing a TTL is therefore a systems decision.

---

# 29. Cache Invalidation

TTL is one form of invalidation.

A more advanced system could proactively remove cached search results when product data changes.

For example:

```text
product update
    ↓
invalidate relevant cached searches
```

However, determining which search queries are affected by a changed product can become difficult.

The current V5 architecture intentionally uses:

```text
TTL-based invalidation
```

because it is simple and predictable.

---

# 30. Negative Caching

A search can legitimately produce:

```text
0 results
```

Those results can also theoretically be cached.

This is called:

```text
negative caching
```

Example:

```text
query:
xyzunknownproduct
```

Without negative caching:

```text
request 1 → DB → 0
request 2 → DB → 0
request 3 → DB → 0
```

With negative caching:

```text
request 1 → DB → 0 → Redis
request 2 → Redis → 0
```

The current architecture can support this because:

```text
count = 0
results = []
```

is still a valid search result.

However, negative-result TTLs may sometimes be kept shorter because new data could make the query valid later.

---

# 31. Cache Metadata

V5 exposes cache information to the frontend.

Example miss:

```json
{
    "cache": {
        "hit": false,
        "lookup_time_ms": 0.8,
        "write_time_ms": 0.6,
        "ttl_seconds": 300
    }
}
```

Example hit:

```json
{
    "cache": {
        "hit": true,
        "lookup_time_ms": 0.5,
        "write_time_ms": 0,
        "ttl_remaining_seconds": 281
    }
}
```

This lets SearchLab visualize the cache behavior directly.

---

# 32. Database Metadata

The response also exposes whether PostgreSQL executed.

Cache miss:

```json
{
    "database": {
        "executed": true,
        "fts_attempted": true,
        "fuzzy_attempted": false
    }
}
```

Cache hit:

```json
{
    "database": {
        "executed": false,
        "fts_attempted": false,
        "fuzzy_attempted": false
    }
}
```

This distinction is essential.

---

# 33. Cache Hit Does Not Mean Search Strategy Is Unknown

Suppose a fuzzy result was originally produced:

```text
query
 ↓
FTS failed
 ↓
pg_trgm succeeded
 ↓
result cached
```

The cached payload can still remember:

```json
{
    "strategy": "fuzzy_fallback",
    "fallback_used": true
}
```

On the next cache hit:

```text
strategy:
fuzzy_fallback
```

describes the algorithm that originally produced the cached result.

But:

```text
database.executed:
false
```

describes the current request.

Those are two different concepts.

# 34. Cache Hit Timing

A cache hit can be measured using:

```python
start = perf_counter()

cached = redis_client.get(
    cache_key
)

end = perf_counter()
```

Then:

```python
lookup_time_ms = (
    end - start
) * 1000
```

This measures the application's observed Redis lookup time.

Conceptually:

```text
total request

Redis lookup
    ↓
FTS
    ↓
optional fuzzy search
    ↓
serialization
    ↓
Redis write
    ↓
response
```

V5 can expose these stages separately.

Example:

```text
Redis lookup:
0.7 ms

FTS:
12.8 ms

Fuzzy:
0 ms

Redis write:
0.6 ms

15.2 ms
```

```text
logtech keybord
```

```text
    ↓
```

# 37. Cache Hit Timing Example

Repeat the exact same logical query.

Now:


# 38. Cold vs Warm Application Search

V5 introduces another meaning of:

```text
cold
```

and:

```text
warm
```

in addition to PostgreSQL buffer caching.

A **cache-cold application request** means:

```text
Redis has no search-result entry
```

A **cache-warm application request** means:

```text
Redis already contains the result
```

This is separate from:

```text
PostgreSQL shared-buffer warmness
```

The two cache layers should not be confused.

---

# 39. PostgreSQL Cache vs Redis Cache

PostgreSQL already caches pages internally.

For example:

```text
Shared Hit Blocks
```

may indicate table/index pages were available in PostgreSQL shared buffers.

Redis caching is different.

## PostgreSQL cache

Still executes:

```text
query planning
query operators
ranking
sorting
result construction
```

even if the required pages are already cached.

## Redis result cache

Can bypass:

```text
PostgreSQL entirely
```

because the final application result is already available.

---

# 40. Why Redis Can Be Much Faster

A PostgreSQL search might require:

```text
parse
plan
GIN lookup
heap fetches
ranking
sort
headline generation
row transfer
```

A Redis hit requires approximately:

```text
GET key
 ↓
receive serialized value
 ↓
deserialize
```

That is a fundamentally smaller amount of work.

---

# 41. Redis Does Not Guarantee Every Request Is Faster

Caching only helps when queries repeat sufficiently often.

Suppose traffic is:

```text
query A
query B
query C
query D
query E
```

and each query appears only once.

Then every request becomes:

```text
Redis MISS
+
database work
+
Redis write
```

Redis adds overhead without producing cache hits.

Therefore caching effectiveness depends heavily on workload.

---

# 42. Cache Hit Rate

One of the most important cache metrics is:

```text
cache hit rate
```

Formula:

```text
cache hits
────────────── × 100
total lookups
```

Example:

```text
800 cache hits
200 cache misses
```

means:

```text
80% hit rate
```

A high hit rate indicates the application is frequently avoiding repeated work.

---

# 43. Cache Miss Rate

The inverse is:

```text
cache miss rate
```

Formula:

```text
cache misses
──────────────── × 100
total lookups
```

If:

```text
20% miss rate
```

then PostgreSQL still executes for approximately one in five searches.

---

# 44. Speedup

V5 can calculate or display the speedup between:

```text
cache miss
```

and:

```text
cache hit
```

For example:

```text
PostgreSQL path:
18.0 ms

Redis path:
1.2 ms
```

Then:

```text
18.0 / 1.2
=
15×
```

The cached request is approximately fifteen times faster for that measurement.

This should be treated as an observed benchmark, not a universal guarantee.

---

# 45. Redis Failure Must Not Break Search

Redis is an optimization.

It should not become the single point that makes the search engine unavailable.

The desired behavior is:

```text
Redis works
    ↓
use cache
```

but:

```text
Redis fails
    ↓
continue to PostgreSQL
```

Therefore V5 catches Redis errors.

Conceptually:

```python
try:
    cached = redis_client.get(key)

except RedisError:
    cached = None
```

Then normal database retrieval continues.

---

# 46. Source of Truth

This establishes an important dependency hierarchy.

```text
PostgreSQL
=
source of truth
```

while:

```text
Redis
=
derived temporary state
```

If Redis loses all cached data:

```text
search should still work
```

The system merely becomes slower until the cache warms again.

---

# 47. Redis Read Failure

Suppose:

```text
redis-server stopped
```

Then:

```text
Redis GET
    ↓
connection error
```

V5 should record the error for diagnostics but continue:

```text
PostgreSQL FTS
    ↓
optional fuzzy fallback
    ↓
results
```

A caching failure should not become a search failure.

---

# 48. Redis Write Failure

Likewise, suppose PostgreSQL successfully returns products but:

```text
Redis SET
```

fails.

The correct behavior is still:

```text
return search results
```

The only consequence is:

```text
result was not cached
```

The next request may need to execute PostgreSQL again.

---

# 49. Graceful Degradation

This behavior is called:

```text
graceful degradation
```

The application loses an optimization while preserving its primary function.

Conceptually:

```text
healthy system:
Redis + PostgreSQL

Redis outage:
PostgreSQL only

PostgreSQL outage:
search unavailable
```

This reflects the actual dependency hierarchy.

---

# 50. `EXPLAIN ANALYZE` on Cache Miss

For SearchLab, database queries can still be inspected using:

```sql
EXPLAIN (
    ANALYZE,
    BUFFERS,
    FORMAT JSON
)
```

But only when PostgreSQL actually participates in the request.

Cache miss:

```text
database executed
→ EXPLAIN may be useful
```

---

# 51. Never Run `EXPLAIN ANALYZE` on a Cache Hit

A cache hit means:

```text
PostgreSQL was bypassed
```

Running:

```sql
EXPLAIN ANALYZE
```

afterward would execute PostgreSQL purely for diagnostics.

That would defeat the purpose of demonstrating a cache hit.

Therefore:

```text
CACHE HIT
    ↓
query_plan = null
    ↓
database.executed = false
```

This is the honest representation.

---

# 52. `EXPLAIN ANALYZE` Is a Lab Feature

The SearchLab application intentionally runs:

```text
EXPLAIN ANALYZE
```

so execution behavior can be inspected.

A production search endpoint normally should not execute:

```sql
EXPLAIN ANALYZE
```

on every request.

It doubles database work for diagnostic purposes.

Therefore V5 can use:

```python
ENABLE_EXPLAIN = True
```

for the lab.

Production-style behavior would be:

```python
ENABLE_EXPLAIN = False
```

# 53. `tracemalloc`

The project continues using:

```python
tracemalloc
```

for Python-side benchmarking.

Example:

```python
tracemalloc.start()
```

followed by:

```python
current_memory, peak_memory = (
    tracemalloc.get_traced_memory()
)
```

This provides educational visibility into Python allocations.

However:

```text
tracemalloc
```

does not measure:

```text
PostgreSQL memory

network buffers
```

It only observes Python memory allocations.

---

# 54. Production Caveat for `tracemalloc`

`tracemalloc` is process-level instrumentation.

Starting and stopping it per request is useful for an isolated SearchLab benchmark.

It is not an ideal production per-request memory measurement technique under high concurrency.

Therefore:

```text
SearchLab:
use it for learning

Production:
use proper observability/profiling systems
```

# 55. Cache Payload vs API Response

The Redis payload and API response should not necessarily be identical.

Redis may store:

```json
{
    "strategy": "full_text",
    "fallback_used": false,
    "engine": "postgresql_fts_gin",
    "count": 14,
    "results": []
}
```

The live API response additionally contains:

```text
cache metadata
request timing
memory data
database execution state
query plan
```

These belong to the current request, not the cached search result.

```text

```

because Redis supplied them.

# 59. Cache Invalidation Problem

Caching introduces one of the classic hard problems in computer science:

```text
When is cached data no longer valid?
```

Possible strategies include:

```text
TTL expiration
explicit invalidation
versioned keys
event-driven invalidation
short-lived cache
manual flush
```

V5 primarily uses:

```text
TTL
+
versioned cache keys
```

---

# 60. Cache Key Must Include Every Result-Changing Input

Today the search cache key is mostly based on:

```text
normalized query
```

But suppose the API later supports:

```text
category filter
price range
rating threshold
sort mode
page number
page size
availability
language
```

Then this would be incorrect:

```text
search:v5:<query>
```

because:

```text
keyboard
price <= 50
```

and:

```text
keyboard
price <= 500
```

could incorrectly share the same cached result.

A mature cache key must encode every input that affects the response.

---

# 61. Pagination and Cache Keys

If pagination is added:

```text
page 1
page 2
page 3
```

must not accidentally share the same cache key unless the complete result set is cached and pagination happens afterward.

Two possible designs are:

```text
cache every page separately
```

or:

```text
cache complete ranked result
then paginate application-side
```

Each has tradeoffs.

For SearchLab, simple query-level caching is sufficient to demonstrate the concept.

---

# 62. Cache Stampede

A more advanced problem occurs when many requests miss the same key simultaneously.

Example:

```text
Redis key expires

100 users request:
"gaming keyboard"

at the same moment
```

All 100 requests could observe:

```text
MISS
```

and all 100 could execute PostgreSQL simultaneously.

This is called:

```text
cache stampede
```

or:

```text
thundering herd
```

V5 does not yet implement stampede protection.

Possible later techniques include:

```text
distributed locks
single-flight requests
stale-while-revalidate
randomized TTL jitter
```

---

# 63. TTL Jitter

If many cache entries are created together with the same TTL:

```text
300 seconds
```

they may also expire together.

A more advanced system might use:

```text
300 ± random seconds
```

to spread expiration times.

This is called:

```text
TTL jitter
```

It reduces synchronized expiration spikes.

This is beyond the current V5 implementation but is an important production caching concept.

---

# 64. Redis Memory Is Finite

Redis primarily stores data in memory.

Therefore cached results consume RAM.

If every possible search query were cached forever:

```text
memory usage
↑
↑
↑
```

This is another reason V5 uses TTLs.

Production systems also configure:

```text
maximum memory
eviction policies
```

to control cache growth.

---

# 65. Cache Eviction

Redis may remove keys before their TTL expires when configured memory limits require eviction.

Possible Redis policies can prioritize:

```text
least recently used
least frequently used
TTL-based candidates
random eviction
```

Therefore:

```text
TTL remaining
```

does not necessarily guarantee an item will remain cached until that exact time under every production configuration.

For SearchLab, local Redis behavior is sufficient.

---

# 66. Cache Hit Does Not Mean Data Is More Correct

A Redis hit can be:

```text
faster
```

but it is not inherently:

```text
more correct
```

Correctness still comes from the search pipeline and the cached data's freshness.

Redis cannot fix:

```text
bad ranking
incorrect fuzzy matches
poor SQL
stale source data
wrong cache keys
```

Caching preserves the result it was given.

---

# 67. Redis Cannot Fix Bad Search Relevance

Suppose V4 returns:

```text
bad product ranking
```

Caching it makes:

```text
bad product ranking
```

faster.

Therefore the engineering sequence matters:

```text
first:
make search correct

then:
make retrieval efficient

then:
add typo tolerance

then:
cache repeated results
```

That is exactly why Redis belongs at the end of SearchLab.

# 82. Cache-Aside Pattern

The architecture used by V5 is commonly called:

```text
cache-aside
```

or:

```text
lazy caching
```

The application itself controls the cache.

Pattern:

```text
1. Check cache

2. If hit:
   return cache

3. If miss:
   read source of truth

4. Put result in cache

5. Return result
```

That is exactly what V5 implements.

---

# 83. Why Cache-Aside Is Useful

Cache-aside keeps Redis optional.

The database remains independent.

If Redis is empty:

```text
application still works
```

If Redis restarts:

```text
application still works
```

The cache simply warms again as requests arrive.

This makes the architecture easy to reason about.

---

# 84. Cache Warm-Up

After Redis starts empty:

```text
cache = {}
```

the first requests populate it gradually.

This process is called:

```text
cache warming
```

Example:

```text
keyboard
→ miss → cached

mouse
→ miss → cached

keyboard
→ hit

headphones
→ miss → cached

mouse
→ hit
```

Popular queries naturally become warm.

---

# 85. Popular Queries Benefit Most

Caching gives the greatest value when query distribution is uneven.

For example:

```text
gaming keyboard      20,000 requests
wireless mouse       15,000 requests
airpods               8,000 requests
random query 123          1 request
```

Popular searches can generate many cache hits.

Rare one-off searches may not benefit significantly.

---

# 86. Query Distribution

Real-world search traffic often follows a long-tail distribution.

A smaller number of popular queries may account for a large portion of requests.

Then there is a long tail of rarely repeated searches.

Caching primarily benefits the:

```text
high-frequency head
```

rather than every query equally.

---

# 87. Cache Security and Privacy

Cache keys and cached payloads should avoid storing sensitive information unnecessarily.

SearchLab uses product-search terms, but a real application might process queries containing private data.

Hashing keys prevents raw query text from appearing directly in the key namespace, although:

```text
hashing
≠
encryption
```

Cached values should still be treated according to application privacy requirements.
