## V2 — PostgreSQL Full-Text Search

### Full-Text Search

Move from raw substring matching to PostgreSQL linguistic retrieval using tokens, lexemes, stemming, `tsvector`, and `tsquery`.

V1 searched for character sequences directly using `LIKE` and `ILIKE`.

For example:

```sql
WHERE title ILIKE '%database%'
```

This works well for basic substring matching, but it does not understand language.

A search for:

```text
develop
```

does not inherently mean:

```text
developer
developers
developed
developing
development
```

Full-text search changes the search model.

Instead of comparing raw strings, PostgreSQL converts text into a normalized representation designed specifically for information retrieval.

---

## The Core Idea

The V2 search pipeline is:

```text
Document text
    ↓
Tokenization
    ↓
Normalization
    ↓
Lexemes
    ↓
tsvector

User query
    ↓
Query parser
    ↓
tsquery

tsvector @@ tsquery
    ↓
Matching documents
    ↓
Relevance ranking
```

The important difference is that PostgreSQL is no longer asking:

```text
Does this exact character sequence occur in the text?
```

It is asking something closer to:

```text
Does this document contain linguistic terms that satisfy this search query?
```

---

# 1. Tokens

PostgreSQL first breaks text into meaningful pieces called **tokens**.

Given:

```text
PostgreSQL developers are building powerful searching systems.
```

PostgreSQL identifies parts such as:

```text
PostgreSQL
developers
are
building
powerful
searching
systems
```

These are the raw linguistic units extracted from the text.

Tokenization also allows PostgreSQL to distinguish between different kinds of input such as:

```text
words
numbers
email addresses
URLs
hostnames
```

The tokens are then processed according to the selected text-search configuration.

For this project, V2 uses:

```sql
'english'
```

---

# 2. Lexemes

Tokens are not stored exactly as they appear.

PostgreSQL normalizes them into **lexemes**.

A lexeme is the normalized form PostgreSQL uses internally for searching.

For example:

```sql
SELECT to_tsvector(
    'english',
    'Developers are developing powerful search systems'
);
```

may produce a representation conceptually similar to:

```text
'develop':1,3
'power':4
'search':5
'system':6
```

Notice what happened:

```text
Developers  → develop
developing  → develop
powerful    → power
systems     → system
```

The original word forms are normalized.

This allows related grammatical forms to match the same search term.

---

# 3. Stemming

This normalization process includes **stemming**.

Stemming reduces related word forms toward a common root-like representation.

For example:

```text
developer
developers
developing
developed
```

can all normalize toward:

```text
develop
```

This is one of the major differences between V1 and V2.

### V1

```sql
ILIKE '%develop%'
```

matches because the literal characters `develop` happen to occur inside those words.

### V2

```text
develop
```

matches because PostgreSQL understands those words through their normalized lexemes.

The distinction becomes much more important for words whose grammatical forms do not behave like convenient substrings.

---

# 4. Stop Words

Full-text search can also remove very common words that usually contribute little search meaning.

For example:

```text
the
a
an
is
are
of
to
and
```

These are known as **stop words**.

Consider:

```sql
SELECT to_tsvector(
    'english',
    'The database is a powerful system'
);
```

The resulting vector may resemble:

```text
'databas':2
'power':5
'system':6
```

Words such as:

```text
the
is
a
```

are ignored.

This reduces noise in the search representation.

---

# 5. `tsvector`

PostgreSQL represents searchable document text using the `tsvector` type.

Example:

```sql
SELECT to_tsvector(
    'english',
    'PostgreSQL provides powerful full text search'
);
```

Example result:

```text
'full':4
'postgresql':1
'power':3
'provid':2
'search':6
'text':5
```

A `tsvector` contains normalized lexemes and their positions inside the source text.

Conceptually:

```text
lexeme → positions
```

Example:

```text
'search':6,12,20
```

means that the normalized term `search` appeared at several positions in the document.

These positions become useful later for:

```text
phrase matching
ranking
proximity
headline generation
```

---

# 6. `tsquery`

The user's search query is represented using PostgreSQL's `tsquery` type.

While `tsvector` represents the document:

```text
Document → tsvector
```

`tsquery` represents the search condition:

```text
User input → tsquery
```

For example:

```sql
SELECT plainto_tsquery(
    'english',
    'database search'
);
```

may produce:

```text
'databas' & 'search'
```

The `&` operator means:

```text
AND
```

Therefore the query requires both terms.

---

# 7. Matching with `@@`

PostgreSQL uses the `@@` operator to determine whether a `tsvector` satisfies a `tsquery`.

Example:

```sql
SELECT
    to_tsvector(
        'english',
        'PostgreSQL provides powerful database search'
    )
    @@
    plainto_tsquery(
        'english',
        'database search'
    );
```

The result is:

```text
true
```

Conceptually:

```text
tsvector @@ tsquery
```

means:

```text
Does this searchable document representation satisfy this search query?
```

This becomes the foundation of V2.

---

# 8. V2 Search Query

Instead of the V1 pattern:

```sql
SELECT *
FROM documents
WHERE title ILIKE '%' || :query || '%'
   OR content ILIKE '%' || :query || '%';
```

V2 uses full-text search:

```sql
SELECT *
FROM documents
WHERE
    to_tsvector(
        'english',
        coalesce(title, '') || ' ' || coalesce(content, '')
    )
    @@
    plainto_tsquery(
        'english',
        :query
    );
```

The document text is converted into a `tsvector`.

The user input is converted into a `tsquery`.

The `@@` operator performs the match.

---

# 9. `coalesce()`

The query uses:

```sql
coalesce(title, '')
```

and:

```sql
coalesce(content, '')
```

because concatenating SQL values with `NULL` can produce `NULL`.

For example:

```sql
'hello' || NULL
```

results in:

```text
NULL
```

Using:

```sql
coalesce(content, '')
```

converts a missing value into an empty string.

This ensures the text can safely be passed into:

```sql
to_tsvector()
```

---

# 10. Query Parsers

PostgreSQL provides several ways to convert user input into a `tsquery`.

The important ones for this project are:

```text
to_tsquery()
plainto_tsquery()
phraseto_tsquery()
websearch_to_tsquery()
```

They serve different purposes.

---

## `to_tsquery()`

```sql
SELECT to_tsquery(
    'english',
    'postgres & search'
);
```

This gives direct access to PostgreSQL's query syntax.

Operators include:

```text
&    AND
|    OR
!    NOT
<->  FOLLOWED BY
```

Example:

```text
postgres & search
```

means:

```text
postgres AND search
```

This parser is powerful, but it expects correctly formatted `tsquery` syntax.

It is therefore not ideal for raw user input.

---

## `plainto_tsquery()`

```sql
SELECT plainto_tsquery(
    'english',
    'postgres search'
);
```

PostgreSQL interprets the words as:

```text
'postgres' & 'search'
```

This is safe and simple.

Users can type normal text without knowing PostgreSQL query syntax.

For the basic V2 implementation, this provides a good starting point.

---

## `phraseto_tsquery()`

```sql
SELECT phraseto_tsquery(
    'english',
    'full text search'
);
```

This preserves the ordering relationship between terms.

Conceptually:

```text
'full' <-> 'text' <-> 'search'
```

This is useful when search terms are expected to appear as a phrase rather than independently anywhere in the document.

---

## `websearch_to_tsquery()`

```sql
SELECT websearch_to_tsquery(
    'english',
    '"full text search" -mysql'
);
```

This supports syntax closer to common search engines.

Users can write queries such as:

```text
postgres database
```

```text
"full text search"
```

```text
postgres OR mysql
```

```text
postgres -mysql
```

without needing to know PostgreSQL's internal `tsquery` syntax.

For an application-facing search interface, this is often more convenient than exposing `to_tsquery()` directly.

---

# 11. Relevance Ranking

V1 mostly answers a binary question:

```text
Did this substring match?
```

V2 introduces another important concept:

```text
How relevant is this result?
```

PostgreSQL provides ranking functions including:

```sql
ts_rank()
```

and:

```sql
ts_rank_cd()
```

For this project, V2 uses:

```sql
ts_rank_cd()
```

Example:

```sql
SELECT
    id,
    title,
    content,

    ts_rank_cd(
        to_tsvector(
            'english',
            coalesce(title, '') || ' ' || coalesce(content, '')
        ),
        plainto_tsquery(
            'english',
            :query
        )
    ) AS rank

FROM documents

WHERE
    to_tsvector(
        'english',
        coalesce(title, '') || ' ' || coalesce(content, '')
    )
    @@
    plainto_tsquery(
        'english',
        :query
    )

ORDER BY rank DESC;
```

Instead of returning matching rows in arbitrary database order, the results can now be ordered by search relevance.

---

# 12. Cover-Density Ranking

`ts_rank_cd()` uses cover-density ranking.

One important idea behind this ranking method is that search terms appearing close together can indicate stronger relevance.

Consider the query:

```text
database indexing
```

### Document A

```text
PostgreSQL database indexing improves query performance.
```

### Document B

```text
Database systems are widely used.

...

Several paragraphs later...

Indexes can improve lookup performance.
```

Both documents may contain matching terms.

However, the first document contains the terms in a much tighter semantic region.

`ts_rank_cd()` can take this positional relationship into account when calculating relevance.

The score should not be interpreted as a universal percentage.

For example:

```text
rank = 0.37
```

does **not** mean:

```text
37% relevant
```

The score is useful primarily for comparing matching documents within the same search query.

---

# 13. Search Result Highlighting

V2 can also generate contextual search snippets using:

```sql
ts_headline()
```

Example:

```sql
SELECT
    ts_headline(
        'english',
        content,
        plainto_tsquery(
            'english',
            'database indexing'
        )
    )
FROM documents;
```

PostgreSQL can return a section of the text containing the matched terms.

This makes it possible for the UI to show something similar to:

```text
PostgreSQL provides powerful database indexing techniques...
```

with matching words highlighted.

A configurable version could use:

```sql
ts_headline(
    'english',
    content,
    plainto_tsquery('english', :query),
    'StartSel=<mark>, StopSel=</mark>'
)
```

This can later be rendered inside the search result interface.

# 14. Weighted Search Fields

Not every part of a document should necessarily contribute equally to relevance.

A search term appearing in the title is often more important than the same term appearing once deep inside the content.

PostgreSQL provides weights:

```text
A
B
C
D
```

where:

```text
A = highest importance
D = lowest importance
```

For example:

```sql
setweight(
    to_tsvector(
        'english',
        coalesce(title, '')
    ),
    'A'
)
||
setweight(
    to_tsvector(
        'english',
        coalesce(content, '')
    ),
    'B'
)
```

This creates one combined document vector while preserving the relative importance of different fields.

Conceptually:

```text
Title   → Weight A
Content → Weight B
```

A title match can therefore contribute more strongly to the relevance score.

---

# 15. V2 Weighted Search Query

The searchable document can be constructed as:

```sql
setweight(
    to_tsvector(
        'english',
        coalesce(title, '')
    ),
    'A'
)
||
setweight(
    to_tsvector(
        'english',
        coalesce(content, '')
    ),
    'B'
)
```

The complete search becomes:

```sql
WITH search_query AS (
    SELECT plainto_tsquery(
        'english',
        :query
    ) AS query
)

SELECT
    d.id,
    d.title,
    d.content,

    ts_rank_cd(
        setweight(
            to_tsvector(
                'english',
                coalesce(d.title, '')
            ),
            'A'
        )
        ||
        setweight(
            to_tsvector(
                'english',
                coalesce(d.content, '')
            ),
            'B'
        ),
        sq.query
    ) AS rank

FROM documents AS d
CROSS JOIN search_query AS sq

WHERE
    (
        setweight(
            to_tsvector(
                'english',
                coalesce(d.title, '')
            ),
            'A'
        )
        ||
        setweight(
            to_tsvector(
                'english',
                coalesce(d.content, '')
            ),
            'B'
        )
    )
    @@ sq.query

ORDER BY rank DESC;
```

The CTE:

```sql
WITH search_query AS (...)
```

prevents us from repeatedly writing the query-construction expression.

# 16. What V2 Improves Over V1

V1 performs textual pattern matching.

V2 performs linguistic information retrieval.

### V1

```text
Raw query
    ↓
Character comparison
    ↓
Substring match
```

### V2

```text
Raw query
    ↓
Tokenization
    ↓
Normalization
    ↓
Stemming
    ↓
tsquery
    ↓
Linguistic matching
    ↓
Relevance ranking
```

This gives V2 several capabilities that V1 does not naturally provide:

* stemming
* stop-word handling
* normalized terms
* Boolean search semantics
* phrase search
* relevance ranking
* weighted fields
* search-result highlighting
* more expressive query parsing

---

# 17. What V2 Does Not Solve

V2 improves **search semantics**, but it does not yet solve the performance problem.

The important limitation is that V2 does **not** use a full-text search index.

The expression:

```sql
to_tsvector(
    'english',
    coalesce(title, '') || ' ' || coalesce(content, '')
)
```

must still be evaluated while PostgreSQL processes the rows involved in the query.

For a large table, PostgreSQL may still perform a:

```text
Sequential Scan
```

Conceptually:

```text
Read row 1
→ construct tsvector
→ test query

Read row 2
→ construct tsvector
→ test query

Read row 3
→ construct tsvector
→ test query

...

Read row N
→ construct tsvector
→ test query
```

Therefore:

```text
V2 improves WHAT PostgreSQL searches.

It does not yet significantly improve HOW PostgreSQL finds those documents.
```

That distinction is intentional.

---

# 18. Expected Execution Plan

When inspecting V2 with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

we may see an execution plan containing:

```text
Seq Scan
```

or:

```text
Sequential Scan
```

This means PostgreSQL scans the table row by row rather than using a specialized full-text index to locate matching documents.

The plan may also contain:

```text
Sort
```

because matched rows must be ordered by their calculated relevance score.

A simplified execution flow is:

```text
Sequential Scan
    ↓
Generate tsvector
    ↓
Apply tsquery
    ↓
Discard non-matching rows
    ↓
Calculate rank
    ↓
Sort by rank
    ↓
Limit results
```

This is expected behavior in V2.

It is not a bug.

---

# 19. Why V2 Exists Separately

It would be easy to introduce full-text search and a GIN index simultaneously.

However, doing so would hide two different improvements behind one version.

V2 isolates the semantic improvement:

```text
Substring Search
        ↓
Linguistic Search
```

The next version will isolate the performance improvement:

```text
Unindexed Linguistic Search
        ↓
Indexed Linguistic Search
```

This allows the project to measure the effect of each architectural decision independently.

| Feature               | V1                         | V2                     |
| --------------------- | -------------------------- | ---------------------- |
| Search model          | substring matching         | linguistic retrieval   |
| Main mechanism        | `LIKE` / `ILIKE`           | `tsvector` + `tsquery` |
| Tokenization          | No                         | Yes                    |
| Lexemes               | No                         | Yes                    |
| Stemming              | No                         | Yes                    |
| Stop words            | No                         | Yes                    |
| Boolean queries       | Limited/manual             | Yes                    |

| Relevance ranking     | No native ranking          | Yes                    |

The most important comparison is:

```text
V1 = raw text matching

V2 = language-aware search without search indexing
```

# 21. Performance Measurements

V2 continues collecting the same measurements as V1 so the versions can be compared fairly.

The application records:

```text
Database execution plan
Planning time
Execution time
Application time
Memory usage
Rows returned
Rows removed by filter
Buffer activity
```

The purpose is not only to determine which query is faster.

We also want to understand:

```text
what work PostgreSQL performed
```

and:

```text
why the query had that performance
```

---

# 22. Application Time

Application time measures the duration observed by the backend around the database operation.

Conceptually:

```python
start = perf_counter()

# execute database search

end = perf_counter()

application_time = end - start
```

This may include work outside the PostgreSQL executor itself, such as:

```text
database communication
Python database-driver overhead
row conversion
result processing
```

Therefore:

```text
Application Time ≠ PostgreSQL Execution Time
```

Both are useful, but they measure different layers.

---

# 23. Memory Measurement

The backend continues using Python memory instrumentation to observe memory allocations during the search operation.

This represents application-side memory behavior.

It should not be interpreted as PostgreSQL server memory consumption.

Conceptually:

```text
Backend memory measurement
        ≠
PostgreSQL internal memory usage
```

Keeping these metrics separate prevents misleading conclusions.

# 24. Reading the V2 Explain Report

The UI should translate PostgreSQL's raw execution plan into understandable information.

For example:

```text
Seq Scan
```

should be presented as:

```text
Sequential Scan

PostgreSQL read through the table row by row because this version does not yet have a specialized full-text search index.
```

---

### Rows Removed by Filter

If PostgreSQL reports:

```text
Rows Removed by Filter: 98,420
```

the UI can explain:

```text
PostgreSQL inspected these rows but rejected them because their generated search vectors did not satisfy the full-text query.
```

A large number is important because it demonstrates how much unnecessary scanning work occurs without an index.

---

### Actual Time

An execution-plan node may contain values similar to:

```text
actual time=2.140..74.820
```

This can be translated as:

```text
Time until the node produced its first row:
2.140 ms

Time until the node finished producing its rows:
74.820 ms
```

These values should not be confused with the complete application response time.

---

### Buffers

A plan may contain information such as:

```text
Buffers: shared hit=850
```

This indicates that PostgreSQL obtained those data pages from its shared buffer cache rather than reading them from storage during that operation.

The report should explain this rather than displaying the raw field without context.

---

# 25. Raw Query and Raw Explain Output

The UI should preserve access to the original technical information.

The human-readable report explains the execution plan.

A dropdown should additionally expose:

```text
Raw SQL Query
Raw EXPLAIN Response
```

This provides two layers:

```text
Human-readable explanation
        +

```

The first helps understand the system.

The second allows verification.

# 26. V2 Learning Outcome

After completing V2, the important concepts to understand are:

```text
token
lexeme
stemming
stop word
text-search configuration
tsvector
tsquery
@@
query parsing
phrase matching
relevance ranking
field weighting
ts_headline
```

But there is an equally important systems lesson:

```text
Better search semantics do not automatically mean better search performance.
```

V2 makes PostgreSQL substantially more capable as a search engine while still forcing it to perform expensive work across the dataset.

That limitation is deliberate.

It establishes the baseline required for the next optimization stage.

# Next: V3 — Indexed Full-Text Search

V2 answers:

```text
How can PostgreSQL understand search terms instead of simply matching characters?
```

The next version answers:

```text
How can PostgreSQL avoid scanning and processing the entire dataset to find those terms?
```

V3 keeps the full-text search semantics introduced here and adds a dedicated **GIN inverted index**.

That allows us to compare:

```text
V2
Full-Text Search
+
Sequential processing

            ↓

V3
Full-Text Search
+
GIN inverted index
```

This separates the two core search-system concerns:

```text
Relevance and semantics → V2

Retrieval efficiency     → V3
```
